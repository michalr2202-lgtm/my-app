Documents components introduced while building the Client Home Screen (`/docs/home-screen-prd.md`). Update this file whenever a reusable component is added or changed on a future screen — do not duplicate an existing entry's functionality without reusing it first.

## `components/ui` — primitives

### `Pill`
`src/components/ui/Pill.tsx`

Generic rounded-full button primitive.

- **Layout:** `rounded-full`, `px-4 py-3` (16/12px), hug-width, no max-width (wraps its text as one line, `whitespace-nowrap`).
- **Typography:** `text-sm font-medium leading-[1.4]` (no `tracking` override - see design-system.md "Typography" letter-spacing rule).
- **Props:** `children`, `colorClassName` (default `text-brand-primary` - no background, changed 2026-09-04 from `bg-surface-pill text-brand-primary`; a caller wanting a filled pill passes its own `colorClassName` explicitly, e.g. `ServicePill`'s per-category background), `style`, plus all native `<button>` props (`onClick`, `disabled`, ...).
- **States:** default, `active:scale-[0.96] active:brightness-95` (pressed), `disabled:opacity-50`.
- **Used by:** `TimePill` (via `TimePillsRow`), `ServicePill`, `ExpandServicesButton` (Popular Services show more/less toggle), `OrderRecap`'s "שנה כתובת" (added 2026-09-04, at `Pill`'s own default styling - no override needed).

### `Button`
`src/components/ui/Button.tsx`

Full-width-capable rounded CTA.

- **Props:** `children`, `variant` (`sheetNext` | `sheetPrevious` | `primary`), plus native `<button>` props.
- **`sheetNext`:** Bottom Sheet mid-flow CTA. Inactive/disabled = `bg-surface-pill text-text-secondary`. Active/enabled = `bg-surface-selected text-brand-primary`.
- **`sheetPrevious`:** Bottom Sheet mid-flow secondary action, paired next to `sheetNext` in a row (`BookingStepFooter`). Transparent background, `text-brand-primary`, always rendered active — no disabled state.
- **`primary`:** brand-filled CTA (`bg-brand-primary text-surface-bg shadow-button`) — reserved for final / "instant" moments; also usable until more sheet variants arrive.
- **States:** default, pressed (`active:scale-[0.96] active:brightness-95`), disabled.

### `Input`
`src/components/ui/Input.tsx`

Generic text field primitive - the first screens to need real form fields beyond the `AttachmentsStep` note `textarea`.

- **Layout:** `rounded-xl border border-divider`, `px-4 py-3`, full width. Optional `label` renders above (`text-sm font-medium text-text-primary`, `gap-1.5` from the field); optional `error`/`helperText` renders below (`text-xs`, `text-notification-red` for error, `text-text-secondary` for helper - error takes precedence when both would apply).
- **Placeholder color:** `placeholder:text-text-secondary/20` when `label` is set (the label already names the field, so the placeholder is just a faint format hint), full-opacity `placeholder:text-text-secondary` when it isn't (the placeholder is then the only instruction for the field - see design-system.md "Forms"). Decided automatically from `label`; override with `placeholderFullOpacity` for the rare labeled field whose placeholder itself carries real information (e.g. `AuthenticationStep`'s OTP field, `"הקוד שקיבלת ב-SMS"`).
- **Props:** `label?`, `error?`, `helperText?`, `placeholderFullOpacity?`, `inputClassName?` (extra classes for the `<input>` itself, e.g. `focus:`/`placeholder:` pseudo-class overrides - see the phone field below), plus all native `<input>` props (`dir` defaults to `"rtl"`). `className` targets the outer wrapper `<div>` instead, same convention as `Combobox` - see design-system.md "Forms" for why the split exists.
- **States:** default, `focus:border-brand-primary`, error (border switches to `border-notification-red`), `disabled:opacity-50`.
- **Used by:** `AuthenticationStep` (phone, OTP code), `NewUserDetailsStep` (name, building number, apartment, entrance code — city/street use `Combobox` instead, see below).

### `Combobox`
`src/components/ui/Combobox.tsx`

Restricted single-select primitive - for fields where the value must be one of a known list, not free text (`NewUserDetailsStep`'s city and street).

- **Layout:** styled like `Input` (same border/radius/padding); tapping the closed field expands its option list **inline below it, in normal document flow** (the same "expand-in-place" pattern as `AuthenticationStep`'s OTP field / `AttachmentsStep`'s note field) rather than an absolutely-positioned floating panel, which would risk being clipped by `BottomSheet`'s scroll container.
- **Props:** `label?`, `value`, `onChange`, `options` (`{value, label}[]`), `placeholder?`, `searchable?` (field becomes a filter-as-you-type input once opened), `searchHint?` (searchable lists only: hides the option list until the query is non-empty, showing this text instead - avoids mounting hundreds of DOM nodes for a long list like street names before the user narrows it down), `disabled?`.
- **Never accepts free text:** even in the `searchable` variant, `value` only ever changes via an explicit tap on a listed option - closing without picking one leaves the previous value untouched.
- **States:** default, open (border switches to `border-brand-primary`, chevron rotates), disabled (`opacity-50`, non-interactive), selected option shows a check icon in the list; the closed field's label truncates with an ellipsis if the selected option's text is too long for the field's width.
- **Placeholder color:** same `label`-conditional rule as `Input` above (`/20` opacity when labeled, full opacity otherwise) - applies to both the searchable variant's native `placeholder` and the closed button's "nothing selected yet" text, which plays the same visual role.
- **Used by:** `NewUserDetailsStep` — city (`searchable` off, 2 short options, its own full-width row) and street (`searchable` + `searchHint`, backed by `src/lib/addresses.ts`'s per-city official street lists, shared row with building number).

### `BottomSheet`
`src/components/ui/BottomSheet.tsx`

Reusable overlay shell (scrim + bottom panel + optional close). See design-system.md "Bottom Sheet".

- **Props:** `open`, `onClose`, `children`, `showCloseButton?` (default true).
- **Behavior:** locks body scroll while open; Escape and scrim tap call `onClose`. Panel is capped at `max-h-[92dvh]` with `overflow-y-auto` as a defensive fallback only - **no step is ever allowed to actually trigger it** (confirmed 2026-08-21: no Bottom Sheet screen may visibly scroll, on any device). Every step's content is independently sized to fit comfortably within that cap; a step that wouldn't fit is split into an additional screen instead (this is why `NewUserDetailsStep`'s full field list was deliberately kept recap-free, and why `ConfirmStep` exists as one dedicated screen instead of any step rendering `OrderRecap` inline on top of its own content - see `ConfirmStep`'s doc comment for the concrete overflow this was caught from). Also carries `[scrollbar-gutter:stable]` (added 2026-09-07) so this desktop scrollbar's width is reserved up front instead of appearing/disappearing as content crosses the `92dvh` cap - without it, a step whose height hovers right at that edge (e.g. `CategoryServiceStep`'s price line appearing under a newly-selected pill) could make the scrollbar pop in, shrink the available width by its few pixels, and reflow a `flex-wrap` pill grid mid-interaction - looked like selecting a pill was itself causing pills to jump, when it was really this scrollbar toggling on the sheet's outer container.

### `CircleFloatButton`
`src/components/ui/CircleFloatButton.tsx`

Floating circular back button — the first genuinely floating-overlay element in the app (added 2026-09-28, Job Details screen, Figma node `9220:6174`). Every other screen's back/nav affordance sits in the normal document flow; this one is deliberately taken out of it.

- **Layout:** `size-[52px]`, `rounded-full`, `bg-surface-bg`, `shadow-button`, wraps a 24px `ChevronRight` (same icon every other back button in the app already uses), `text-brand-primary` (corrected 2026-09-29 from `text-text-primary` - the chevron is brand blue in Figma; only the glyph is brand-colored, the circle background stays neutral).
- **Rendered via `createPortal(..., document.body)`** (fixed 2026-09-30 — a real regression, reported live: the button was scrolling away instead of staying put, the opposite of its one explicit requirement, "שהוא לא זז כשגוללים"). Previously relied on its host screen's root div carrying `will-change-transform` to scope its `fixed` position to the visible `max-w-[480px]` column instead of the true browser edge — but that div is an ordinary content-height flow element, not itself pinned to anything, so "fixed relative to it" meant the button scrolled away with it (the same containing-block mechanism that separately broke `ImageLightbox`, fixed the same day — see that component's doc comment). Portaling straight to `document.body` makes this immune to whatever CSS any host screen's ancestors use.
- **`mounted` guard** (same day, immediately after the portal fix above): unlike `ImageLightbox` (closed by default — its own `if (!open) return null` already skips `document.body` on every render before any user interaction, client or server), this button has no "closed" state; it's always meant to be visible. Calling `createPortal(..., document.body)` unconditionally therefore also ran during Next.js's *server-side* render of this `"use client"` component (client components are still server-rendered for the initial HTML), crashing with `document is not defined` — caught live via the Next.js dev overlay on a page reload, not by the type checker or lint. Fixed with a `mounted` state flipped `true` in a `useEffect` (which never runs server-side); renders nothing for one tick, then the real portaled button — no visible flash, well within a frame, before anything paints.
- **Position:** `fixed` (not `absolute` — required so it stays put while the page scrolls), recomputed for life directly under `<body>`: `top-[calc(env(safe-area-inset-top)+1rem)]` (was `top-4` — a portaled `fixed` child of `<body>` ignores `<body>`'s own safe-area padding, `layout.tsx`, so this button now adds that same inset itself, landing at the identical position verified 2026-09-29 via a simulated real device notch) and `right-[calc(max(0px,(100vw-480px)/2)+1rem)]` (was `right-4` — the RTL-native equivalent of Figma's `top-[16px]`/`left-[307px]` inset, but computed against this app's own actual centered-column margin instead of the raw viewport edge, so it lands 16px inside the visible `max-w-[480px]` column on desktop too, not just on the single-column mobile widths this originally shipped and was checked against).
- **Props:** `aria-label` (required), plus native `<button>` props (`onClick`, `className`, ...).
- **Used by:** `JobDetailsScreen`.

### `ImageLightbox`
`src/components/ui/ImageLightbox.tsx`

Full-viewport photo preview, added 2026-09-28 (Job Details screen) per product direction: tapping an attached photo should show it large, over the same scrim `BottomSheet` uses — "בדיוק אותו דבר כמו כשנפתח bottom sheet".

- **Props:** `src: string | null` (the photo to preview; `null` = closed — no separate `open` prop, since the caller always already knows the URL it wants shown), `onClose`.
- **Layout:** Same `fixed inset-0 z-50` full-viewport scrim/`max-w-[480px]` column-scoping approach as `BottomSheet`, but the photo is centered in the viewport rather than docked to the bottom (this is a preview, not a form step), and the scrim uses its own heavier `bg-overlay-scrim-heavy` (85% black, `design-system.md`'s Colors table) rather than the shared 70% `bg-overlay-scrim` — a deliberately darker dim than any other overlay in the app. The `<img>` itself is never cropped — `object-contain` inside a box capped at `max-w-[calc(100%-2rem)] max-h-[80dvh]` (the same 16px edge inset every screen already uses via `px-4`) preserves its real aspect ratio, scaled down only as far as needed to fit (verified directly via `naturalWidth`/`naturalHeight` vs. rendered box dimensions on a real uploaded 2160×3840 photo, 2026-09-29 — exact ratio match, no cropping).
- **Rendered via `createPortal(..., document.body)`** (fixed 2026-09-29 — a real bug, reported as "a tall photo looks cut off at the top"): `JobDetailsScreen`'s root has `will-change-transform` (for `CircleFloatButton`'s own unrelated fixed-positioning fix, above), which per spec also silently makes that wrapper a containing block for *any* `fixed` descendant, including this component when rendered in place there — re-scoping its overlay into a nested stacking context that then composited *behind* two of its own earlier DOM siblings (the character illustration, `BottomNavigation`) instead of above them. The photo itself was never actually cropped — the illustration was bleeding through on top of it, which only became visible once a photo rendered tall enough to reach that same vertical band (a small/square photo never did, which is why the symptom looked size/aspect-ratio-dependent). Portaling straight to `document.body` makes this overlay immune to whatever CSS *any* caller's ancestors use, present or future — the correct general pattern for a true full-viewport modal, not a one-off patch.
- **Entrance animation** (added 2026-09-28, per product direction: an instant "בום" open felt too abrupt) — scrim `opacity` 0→1 over 300ms `ease-out`; photo `opacity` 0→1 *and* `scale-95`→`scale-100` together over 350ms `cubic-bezier(0.16,1,0.3,1)` (a fast-start/soft-landing curve — see `design-system.md`'s "Interaction & Motion"). Implemented as a manual `entered` flag flipped one frame after mount (`requestAnimationFrame`), not synchronously, since a CSS transition needs the browser to actually paint the "start" state before it can animate toward the next one. No matching exit animation — only the open was the product ask; closing removes the photo immediately.
- **Behavior:** locks body scroll while open; Escape and scrim tap call `onClose` (same technique as `BottomSheet`, duplicated rather than shared since `BottomSheet`'s panel is bottom-docked and this one isn't — sharing would mean threading a "docked vs. centered" prop through a component whose entire contract today is "it's a bottom sheet").
- **Used by:** `JobDetailsScreen` (each attached-photo thumbnail button).

## `components/shared` — cross-screen components

### `OrderCard`
`src/components/shared/OrderCard.tsx`

Shared visual shell for any job-status card shown to the customer — extracted 2026-09-08 from `ActiveJobCard` (below, now a thin wrapper around this) once the Orders screen (`project-prd.md` §6, Figma node `8057:6297`) needed the identical structure for 3 more card kinds beyond the Home Screen's single "active now" card.

- **Layout:** built on `Card`; internal `flex-col gap-6 px-6 py-5`. Row spacing is **not** a uniform gap between all 3 rows - verified via `get_design_context` on the isolated Figma node (2026-07-31): category/date row and name/time row are grouped together with `gap-1` (4px) between them, then `gap-4` (16px) before the service/price row, then `gap-6` (24px) before the centered `StatusBar`.
- **Background:** dynamic, via `resolveCategoryBackground()` (see design-system.md category color decision).
- **Props:** `job: ActiveJob`, `showProfessionalName?` (default `true` — `false` renders the name text with `opacity-0`, preserving row height/alignment rather than collapsing it, matching the Figma export exactly), `showServiceRow?` (default `true` — `false` omits the whole service/price row, genuinely shorter card, not a placeholder), `showFinalPrice?` (default `false` — added 2026-09-29; when `true` and `job.finalPrice` is set, the price side of that row shows `formatFinalPrice(job.finalPrice)` — one real number — instead of `formatPriceRange(priceMin, priceMax)`), `statusVariant?: "active" | "default"` (default `"active"`, passed straight to `StatusBar`), `statusLabel: string` (the pill's text — caller-supplied, since different card kinds need different wording, not derived internally via `getJobStatusLabel`), `onClick?`.
- **States:** default, pressed (`active:brightness-95` via `Card interactive`).
- **Behavior notes:** date shows "היום" if the scheduled date is today, else "יום ה', DD.MM" (`src/lib/formatDate.ts`). Time window is scheduled time → +2h, per the PRD's documented 2-hour slot rule (the Figma sample shows a 1-hour example, treated as illustrative, not a rule). Currency/time strings use `dir="ltr"` to avoid RTL bidi reordering.
- **Status → bucket → variant mapping** (Orders screen, all 4 card kinds otherwise visually identical per the Figma design): "active now" (`on_the_way`/`arrived`/`in_progress`/`waiting_for_customer`/`waiting_for_professional` — the job is actively in flight) → `statusVariant="active"`, label via `getJobStatusLabel`, full card; "confirmed/upcoming" (`confirmed`/`pending_approval`/`rescheduled`) → `statusVariant="default"`, `ordersScreen.upcomingStatusLabel`, full card; "pending acceptance" (`searching_professional` only — no professional assigned yet) → `statusVariant="default"`, `ordersScreen.pendingStatusLabel`, `showProfessionalName={false}`; "history" (`completed`/`cancelled`/`incomplete_work`, last 5, fixed count-only cap - see `orders.ts`'s `HISTORY_LIMIT`) → `statusVariant="default"`, `ordersScreen.historyCompletedStatusLabel` for `completed` (the generic `jobStatus.*` map for the other two), `showServiceRow={job.finalPrice != null}` + `showFinalPrice` (changed 2026-09-29 from an always-`false` `showServiceRow` - a `completed` job now shows its real single `final_price`; `cancelled`/`incomplete_work` still omit the row entirely, since they never have one). `draft` never appears here (pre-submission, not a real order yet).

### `NotificationBanner`
`src/components/shared/NotificationBanner.tsx`

Single top urgent/critical banner. Built generically against the **full** icon/tone system in `/docs/notification_system_prd.md` (not just the one "cancelled" example from Figma) — see `src/lib/notificationVisuals.ts` for the type → icon/tone mapping.

- **Layout:** `rounded-full`, `py-3 pl-3 pr-6`, `gap-2`, icon (24px, first, **right**) + `flex-1` message text (second, **left**) — final result confirmed on 2026-08-02 via direct pixel measurement of Figma's rendered export (node `8168:6167`): icon's right edge sits exactly `24px` from the container's right edge; the text node is a fixed `275px`-wide box with the ink **right-aligned inside it** (so the visible glyphs don't reach the box's left edge - don't assume ink-width == box-width when doing this math). Two earlier passes got this backwards (first assumed the "typical" text-right/icon-left arrangement, then over-corrected the padding after confirming icon-right/text-left but before accounting for the text box's true width) - if re-deriving this from scratch, verify against actual rendered pixels, not just the raw exported class names or `get_metadata` node widths taken at face value.
- **Props:** `message`, `icon` (LucideIcon) and/or `iconSrc` (custom SVG, takes precedence), `tone` (`success | live | reminder | problem | info`), `unread?` (bold vs. regular text, **defaults to `false`**), `onClick?`.
- **States:** unread = `font-semibold`, read/default = `font-normal`. Default changed from `true` to `false` on 2026-07-31: Figma's only concrete reference (a critical "cancelled" banner) renders regular weight, not bold, so that's the safer default absent a confirmed read/unread source for this specific banner. Pressed = `active:brightness-95`.
- **Icon note (2026-07-31):** the "cancelled" type uses a custom SVG (`public/icons/notification-cancelled.svg`, downloaded directly from the Figma node) instead of a `lucide-react` icon, since Figma's `CancelIcon` is a solid/filled glyph that looks meaningfully different from lucide's outline-style `XCircle`. Other types still use `lucide-react` icons (tinted via `tone`) as first-pass placeholders, since Figma provides no reference for them yet — swap to custom SVGs the same way once real examples exist.
- **Open item:** `job_updates.type` → icon mapping slugs in `notificationVisuals.ts` are a first-pass inference (the PRD only gives one literal example, `type: 'delay'`) — confirm/standardize once real `job_updates` rows exist.

### `LoginSheet`
`src/components/shared/LoginSheet.tsx`

Standalone phone-verification `BottomSheet`, added 2026-09-28 to close a real gap: this app only ever creates a session as a side effect of placing an order (`BookingFlowSheet`'s own Authentication step) — there was previously no way for a returning customer to just log in on a *different* device/browser than the one they originally booked with, to see their existing orders, without re-answering category/service/scheduling questions. Sessions are per-browser cookies (`src/lib/supabase.ts`/`src/proxy.ts`) — switching devices always looks like "logged out" from the server's side, same as any session-based app; there's no way to avoid that, only to make re-identifying quick.

- **Reuses `AuthenticationStep`** (`components/client/booking`) exactly as `BookingFlowSheet` does — same `supabase.auth.signInWithOtp`/`verifyOtp` calls, same `pendingPhone`-tracking pattern — only its `heading`/`subheading` are overridden (`login.heading`/`login.subheading`) since the booking copy talks about placing an order right now, which doesn't apply here. Every other string (phone/code labels+placeholders, error messages, button labels) is the exact same `bookingFlow.authentication.*` copy, unchanged.
- **Props:** `open`, `onClose`.
- **On success:** closes itself and calls `router.refresh()` (not a full reload) — the session is already synced to cookies by `verifyOtp`'s own client, so this just re-runs the current route's Server Component with that cookie now present; the real per-customer data appears immediately.
- **Used by:** `AccountLoginPrompt` (below) — not called directly by any screen since 2026-09-29 (was `OrdersScreen`'s empty state directly before that). Deliberately placed under `components/shared`, not `client/orders` — the same gap applies anywhere a screen depends on a session.

### `AccountLoginPrompt`
`src/components/shared/AccountLoginPrompt.tsx`

Extracted 2026-09-29 from `OrdersScreen`'s own inline empty-state block, once `NotificationsScreen`/`ProfileScreen` (both scaffolded the same day, see `components/client/notifications`/`components/client/profile` below) needed the exact same "logged out, might still have history" prompt — a neutral message plus a link that opens `LoginSheet` above. Owns its own `loginOpen` state internally so callers don't each re-implement it.

- **Props:** `message` (the only thing that varies per caller — e.g. `ordersScreen.emptyMessage`).
- **Copy:** the link itself is `shared.accountPrompt.existingCustomerLoginLink` — one shared string, not one per screen, since every caller opens the exact same `LoginSheet` for the exact same reason.
- **Used by:** `OrdersScreen` (`components/client/orders`), `NotificationsScreen` (`components/client/notifications`), `ProfileScreen` (`components/client/profile`).

**Login entry points (architecture decision, confirmed 2026-09-29):** there is no centralized login screen and no Home-screen login button/first-launch gate. This is deliberate, not a gap — `project-prd.md` §2 already states a customer "can create a job without prior login," and the Product Principles list "fast booking over feature richness" / "reduce customer decision-making whenever possible"; a login wall before browsing, or an upfront "log in?" intro screen, would reverse that. Instead: **first login** is implicit — a session is created as a side effect of placing an order (phone OTP in the Booking Flow recognizes an existing customer automatically, no separate action needed). **Second login** (a returning customer with no session on this device/browser) is explicit — `LoginSheet`, surfaced via this exact `AccountLoginPrompt` on every screen whose content actually depends on a session (Orders, Notifications, Profile), rather than duplicated ad hoc per screen or centralized in one place a customer has to go find. This also matches common practice in comparable apps (Uber's Activity tab, Airbnb's Trips tab): browsing/Home stays fully open, and the "log in to see this" prompt only ever appears exactly where it's needed. Separately: a "customer or professional?" selection screen is not needed for MVP at all — `project-prd.md` §14/§15 already establishes professionals are created manually via database, with public professional signup explicitly out of scope: professionals never open this app in MVP, so there is no role to ask a customer about. Revisit only once self-service professional signup actually ships.

## `components/client/home` — Home Screen-specific

- **`ClientHomeScreen`** — top-level orchestrator (`'use client'`); composes all sections; owns the stubbed click handlers (`console.log` + `TODO` comments) for the not-yet-built Bottom Sheet flows. Main content wrapper is `pt-10 pb-6` (changed 2026-09-04 from `py-6` — top padding to whichever section renders first (`ActiveJobCard` / `NotificationBanner` / `SearchSection`, state-dependent) is 40px, deliberately more than the 24px bottom padding above the bottom nav divider).
- **`SearchSection`** — wraps `SearchBar` + `TimePillsRow`, `gap-6`.
- **`SearchBar`** — controlled text input; only triggers `onSearch` on Enter or clicking the search icon (no auto-search, per PRD 3.3).
- **`TimePillsRow`** — the 2 scheduling entry pills, DOM order "דחוף עכשיו" (first, right) then "לקבוע למועד אחר" (second, left) — matches an isolated Figma node screenshot exactly (verified 2026-07-31; visually non-obvious, don't re-swap without re-checking).
- **`CategorySection`** — heading + row of `CategoryCard`, `justify-between`. ## `job_attachments` (photo persistence)

Customer-uploaded booking photos (`AttachmentsStep`) are now persisted, added 2026-09-08 — see `supabase/sql/job_attachments.sql` (RLS + Storage bucket, run manually — this repo has no migrations set up) for the full design notes. `public.job_attachments` itself already existed in Supabase (same as `job_assignments`/`job_updates` — created outside this repo's SQL files) with its own shape: `job_id`, `user_id` (whoever uploaded it, `auth.uid()` — not a `'customer' | 'professional'` text tag), `content_type` (a coarse `'image' | 'note'` row-kind tag, NOT a MIME type despite the name — confirmed via its own check constraint after a real insert failure), `file_url` (a private Storage object *path*, not a public URL — no separate filename column), `text_content` (unused by this feature, which only ever inserts `'image'` rows — a job's note lives on `jobs.notes` directly). Both RLS policies check "is this job's customer, OR an assigned professional" — the same shape already covers a future professional-side upload with zero schema or policy change, once that side has its own session.

- **`src/lib/queries/jobAttachments.ts`** (`uploadJobAttachments`) — uploads each photo to the private `job-attachments` Storage bucket (path: `{jobId}/{uuid}.{ext}` — `{jobId}` prefix is load-bearing, the Storage RLS policies parse it back out; extension-only, no original file name at all — fixed 2026-09-08 after a real upload hit Supabase Storage's "Invalid key" error from a Hebrew/space/parenthesis-containing original name) and inserts a matching `job_attachments` row (`user_id` from `auth.getUser()`, not threaded through as a parameter). Called fire-and-forget from `BookingFlowSheet.submitBooking` right after `submit_booking` returns the new job id — deliberately does not block or fail the booking if a photo upload has an issue, since the job itself is already committed by that point. **Retries (added 2026-09-29):** both the Storage upload and the `job_attachments` insert go through a shared `withRetries` helper (3 attempts, linear backoff) — fixed after a real photo was silently, permanently dropped from a single transient `"Failed to fetch"` (a mobile network blip) with zero retry at all. `withRetries` takes an optional `treatAsSuccess` predicate for the one hazard retrying introduces — a request that actually succeeded server-side but whose response never reached the client would make a plain retry fail with a real "already exists" conflict; the upload call site passes `isAlreadyExistsError` to treat that case as success instead of a 4th failure. The insert call has no such hazard (no unique constraint on the table) and passes none.
- **`src/lib/queries/jobAttachments.ts`** (`fetchJobPhotoUrls`, added 2026-09-28) — the read-side counterpart, for `JobDetailsScreen`. Selects a job's `'image'` rows ordered by `created_at asc`, then exchanges each private `file_url` path for a short-lived (1h) signed URL via `createSignedUrl` — never throws, a signing failure just drops that one photo (logged) rather than failing the whole screen.

## Job status transition RPCs (`supabase/sql/job_transitions.sql`) + dev test harness

Added 2026-09-09, closing the loop discussed at length with the user: before this, `submit_booking` was the *only* thing in the repo that ever wrote to `jobs.status` (creates it at `searching_professional`) — everything past that point (`project-prd.md` §5) was documented only, with no professional auth/app/RPC at all. Deliberately scoped to NOT build the professional app yet — see this file's own header comment for the full reasoning (why validating the backend contract via an internal test tool, before the professional app exists, is lower-risk than building the professional app on top of never-yet-exercised transition logic).

- **`accept_job(p_job_id, p_professional_id)`** — the real "first professional to accept wins" transition (`project-prd.md` §5 "Accept Job"): atomically `searching_professional` → `confirmed` (only succeeds if the job is still unassigned), inserts the real `job_assignments` row, logs a `job_updates` row (`professional_assigned`) so the notification-banner read path gets exercised too. Skips modeling `pending_approval` as its own step — see the SQL file's own comment on that simplification.
- **`advance_job_status(p_job_id, p_new_status)`** — one shared RPC for every status past `confirmed` (`on_the_way`/`arrived`/`in_progress`/`completed`/`cancelled`/etc.) rather than one bespoke RPC per status. **As of 2026-09-09, validates `p_new_status` against a real transition graph keyed on the job's current status** — see `docs/order-model.md`'s "Confirmed Transition Graph (v1)" section for the full graph, its confirmed decisions (`cancelled` is permanently terminal; `rescheduled` always resolves back to `confirmed`), and its explicitly-open questions (the cancellation cutoff, and whether `incomplete_work` survives as its own status — it's currently unreachable).
  - **Fix (2026-10-01):** added `searching_professional → cancelled` and `pending_approval → cancelled` to this graph — both were already documented in `order-model.md`'s graph (the former explicitly, the latter via `cancellation-and-rescheduling.md`'s scope) but neither branch actually existed in the SQL, so either would have raised rather than succeeded. Closed specifically to unblock `JobDetailsScreen`'s new customer self-service cancel (`ReportProblemSheet`, see above), which cancels a `searching_professional` job unconditionally. `rescheduled` deliberately still only allows `→ confirmed` — adding `cancelled` there would contradict the already-confirmed "`rescheduled` always resolves back to `confirmed`" decision (`order-model.md`), so a `rescheduled` job's self-cancel (if `canSelfServiceCancel` is true for one) would currently fail server-side with an inline error rather than succeed; not fixed, since `rescheduled` can't occur in any real data today (no professional app exists yet to put a job there) — revisit once it can.
- **`src/lib/jobStatusTransitions.ts`** (`JOB_STATUS_TRANSITIONS` / `getValidNextStatuses`) — a TS mirror of that same graph, used only for UI-filtering (deciding which action buttons to show); the SQL RPC is the enforced source of truth, this map just avoids a round-trip to discover an illegal transition is illegal.
- **What's real vs. provisional**: the write logic itself (both RPCs) is the same contract the eventual professional app will call — nothing here needs to change or be rewritten later. What IS temporary, both clearly flagged in the SQL file: (1) both RPCs take an explicit actor id/status as a parameter instead of reading it from a real professional's own `auth.uid()` session, since no professional login exists yet; (2) both are granted to `authenticated` (not revoked, unlike `delete_address`/`restore_address`) so the dev harness below can call them from a signed-in customer's own browser session; (3) the transition graph itself has open questions (see above) not yet finalized. Items (1)-(2) must be tightened (grant revoked, `auth.uid()` used instead of a parameter) once a real professional session exists or this app is exposed beyond internal testing.
- **`src/app/dev/job-actions/page.tsx`** — the dev-only test harness itself: lists the signed-in customer's own real jobs (RLS-scoped, no explicit filter needed) with one button per RPC call, **now filtered through `getValidNextStatuses` so only the currently-legal next statuses are shown per job** (added 2026-09-09, same pass as the RPC validation — also doubles as a live check that the TS mirror and SQL graph agree). Not linked from `BottomNavigation` or anywhere else, not in this file's component catalog otherwise, deliberately undesigned (no `Card`/design-system components) as a signal that it isn't a real screen. Delete once a real professional app exists to do this for real.
