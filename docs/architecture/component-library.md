# Component Library

Documents components introduced while building the Client Home Screen (`/docs/home-screen-prd.md`). Update this file whenever a reusable component is added or changed on a future screen — do not duplicate an existing entry's functionality without reusing it first.

## `components/ui` — primitives

### `Pill`
`src/components/ui/Pill.tsx`

Generic rounded-full button primitive.

- **Layout:** `rounded-full`, `px-4 py-3` (16/12px), hug-width, no max-width (wraps its text as one line, `whitespace-nowrap`).
- **Typography:** `text-sm font-medium leading-[1.4]` (no `tracking` override - see design-system.md "Typography" letter-spacing rule).
- **Props:** `children`, `colorClassName` (default `bg-surface-pill text-brand-primary`), `style`, plus all native `<button>` props (`onClick`, `disabled`, ...).
- **States:** default, `active:scale-[0.96] active:brightness-95` (pressed), `disabled:opacity-50`.
- **Used by:** `TimePill` (via `TimePillsRow`), `ServicePill`, `ExpandServicesButton` (Popular Services show more/less toggle).

### `Button`
`src/components/ui/Button.tsx`

Full-width-capable rounded CTA.

- **Props:** `children`, `variant` (`sheetNext` | `sheetPrevious` | `primary`), plus native `<button>` props.
- **`sheetNext`:** Bottom Sheet mid-flow CTA. Inactive/disabled = `bg-surface-pill text-text-secondary`. Active/enabled = `bg-surface-selected text-brand-primary`.
- **`sheetPrevious`:** Bottom Sheet mid-flow secondary action, paired next to `sheetNext` in a row (`BookingStepFooter`). Transparent background, `text-brand-primary`, always rendered active — no disabled state.
- **`primary`:** brand-filled CTA (`bg-brand-primary text-surface-bg shadow-button`) — reserved for final / "instant" moments; also usable until more sheet variants arrive.
- **States:** default, pressed (`active:scale-[0.96] active:brightness-95`), disabled.

### `Input`
`src/components/ui/Input.tsx`

Generic text field primitive - the first screens to need real form fields beyond the `AttachmentsStep` note `textarea`.

- **Layout:** `rounded-xl border border-divider`, `px-4 py-3`, full width. Optional `label` renders above (`text-sm font-medium text-text-primary`, `gap-1.5` from the field); optional `error`/`helperText` renders below (`text-xs`, `text-notification-red` for error, `text-text-secondary` for helper - error takes precedence when both would apply).
- **Placeholder color:** `placeholder:text-text-secondary/20` when `label` is set (the label already names the field, so the placeholder is just a faint format hint), full-opacity `placeholder:text-text-secondary` when it isn't (the placeholder is then the only instruction for the field - see design-system.md "Forms"). Decided automatically from `label`; override with `placeholderFullOpacity` for the rare labeled field whose placeholder itself carries real information (e.g. `AuthenticationStep`'s OTP field, `"הקוד שקיבלת ב-SMS"`).
- **Props:** `label?`, `error?`, `helperText?`, `placeholderFullOpacity?`, `inputClassName?` (extra classes for the `<input>` itself, e.g. `focus:`/`placeholder:` pseudo-class overrides - see the phone field below), plus all native `<input>` props (`dir` defaults to `"rtl"`). `className` targets the outer wrapper `<div>` instead, same convention as `Combobox` - see design-system.md "Forms" for why the split exists.
- **States:** default, `focus:border-brand-primary`, error (border switches to `border-notification-red`), `disabled:opacity-50`.
- **Used by:** `AuthenticationStep` (phone, OTP code), `NewUserDetailsStep` (name, building number, apartment, entrance code — city/street use `Combobox` instead, see below).

### `Combobox`
`src/components/ui/Combobox.tsx`

Restricted single-select primitive - for fields where the value must be one of a known list, not free text (`NewUserDetailsStep`'s city and street).

- **Layout:** styled like `Input` (same border/radius/padding); tapping the closed field expands its option list **inline below it, in normal document flow** (the same "expand-in-place" pattern as `AuthenticationStep`'s OTP field / `AttachmentsStep`'s note field) rather than an absolutely-positioned floating panel, which would risk being clipped by `BottomSheet`'s scroll container.
- **Props:** `label?`, `value`, `onChange`, `options` (`{value, label}[]`), `placeholder?`, `searchable?` (field becomes a filter-as-you-type input once opened), `searchHint?` (searchable lists only: hides the option list until the query is non-empty, showing this text instead - avoids mounting hundreds of DOM nodes for a long list like street names before the user narrows it down), `disabled?`.
- **Never accepts free text:** even in the `searchable` variant, `value` only ever changes via an explicit tap on a listed option - closing without picking one leaves the previous value untouched.
- **States:** default, open (border switches to `border-brand-primary`, chevron rotates), disabled (`opacity-50`, non-interactive), selected option shows a check icon in the list; the closed field's label truncates with an ellipsis if the selected option's text is too long for the field's width.
- **Placeholder color:** same `label`-conditional rule as `Input` above (`/20` opacity when labeled, full opacity otherwise) - applies to both the searchable variant's native `placeholder` and the closed button's "nothing selected yet" text, which plays the same visual role.
- **Used by:** `NewUserDetailsStep` — city (`searchable` off, 2 short options, its own full-width row) and street (`searchable` + `searchHint`, backed by `src/lib/addresses.ts`'s per-city official street lists, shared row with building number).

### `BottomSheet`
`src/components/ui/BottomSheet.tsx`

Reusable overlay shell (scrim + bottom panel + optional close). See design-system.md "Bottom Sheet".

- **Props:** `open`, `onClose`, `children`, `showCloseButton?` (default true).
- **Behavior:** locks body scroll while open; Escape and scrim tap call `onClose`. Panel is capped at `max-h-[92dvh]` with `overflow-y-auto` as a defensive fallback only - **no step is ever allowed to actually trigger it** (confirmed 2026-08-21: no Bottom Sheet screen may visibly scroll, on any device). Every step's content is independently sized to fit comfortably within that cap; a step that wouldn't fit is split into an additional screen instead (this is why `NewUserDetailsStep`'s full field list was deliberately kept recap-free, and why `ConfirmStep` exists as one dedicated screen instead of any step rendering `OrderRecap` inline on top of its own content - see `ConfirmStep`'s doc comment for the concrete overflow this was caught from).

### `Card`
`src/components/ui/Card.tsx`

Generic rounded surface container.

- **Layout:** `w-full`, `rounded-card` (24px), `shadow-card`. Padding is NOT baked in (children control their own padding) since not every future card usage may need the same 24/20px padding as ActiveJobCard.
- **Props:** `children`, `interactive` (adds press feedback: `active:brightness-95`), plus all native `<div>` props.
- **Used by:** `ActiveJobCard`.

### `StatusBar`
`src/components/ui/StatusBar.tsx`

Small rounded status-label pill (name preserved exactly from the Figma layer name — represents a **job status label**, not a device status bar).

- **Layout:** `rounded-full`, `px-3 py-1.5` (12/6px), hug-width.
- **Typography:** `text-sm leading-[1.4]` (no `tracking` override - see design-system.md "Typography" letter-spacing rule), `text-surface-bg` (white) on `bg-brand-primary`.
- **Props:** `children`.
- **Used by:** `ActiveJobCard` (job status: "בדרך אלייך", "הגיע", etc. — see `src/lib/jobStatus.ts`).

## `components/shared` — cross-screen components

### `ActiveJobCard`
`src/components/shared/ActiveJobCard.tsx`

Shown when the customer has a job that isn't `completed`/`cancelled`. See `/docs/home-screen-prd.md` 3.1.

- **Layout:** built on `Card`; internal `flex-col gap-6 px-6 py-5`. Row spacing is **not** a uniform gap between all 3 rows - verified via `get_design_context` on the isolated Figma node (2026-07-31): category/date row and name/time row are grouped together with `gap-1` (4px) between them, then `gap-4` (16px) before the service/price row, then `gap-6` (24px) before the centered `StatusBar`.
- **Background:** dynamic, via `resolveCategoryBackground()` (see design-system.md category color decision).
- **Props:** `job: ActiveJob`, `onClick?`.
- **States:** default, pressed (`active:brightness-95` via `Card interactive`).
- **Behavior notes:** date shows "היום" if the scheduled date is today, else "יום ה', DD.MM" (`src/lib/formatDate.ts`). Time window is scheduled time → +2h, per the PRD's documented 2-hour slot rule (the Figma sample shows a 1-hour example, treated as illustrative, not a rule). Currency/time strings use `dir="ltr"` to avoid RTL bidi reordering.

### `NotificationBanner`
`src/components/shared/NotificationBanner.tsx`

Single top urgent/critical banner. Built generically against the **full** icon/tone system in `/docs/notification_system_prd.md` (not just the one "cancelled" example from Figma) — see `src/lib/notificationVisuals.ts` for the type → icon/tone mapping.

- **Layout:** `rounded-full`, `py-3 pl-3 pr-6`, `gap-2`, icon (24px, first, **right**) + `flex-1` message text (second, **left**) — final result confirmed on 2026-08-02 via direct pixel measurement of Figma's rendered export (node `8168:6167`): icon's right edge sits exactly `24px` from the container's right edge; the text node is a fixed `275px`-wide box with the ink **right-aligned inside it** (so the visible glyphs don't reach the box's left edge - don't assume ink-width == box-width when doing this math). Two earlier passes got this backwards (first assumed the "typical" text-right/icon-left arrangement, then over-corrected the padding after confirming icon-right/text-left but before accounting for the text box's true width) - if re-deriving this from scratch, verify against actual rendered pixels, not just the raw exported class names or `get_metadata` node widths taken at face value.
- **Props:** `message`, `icon` (LucideIcon) and/or `iconSrc` (custom SVG, takes precedence), `tone` (`success | live | reminder | problem | info`), `unread?` (bold vs. regular text, **defaults to `false`**), `onClick?`.
- **States:** unread = `font-semibold`, read/default = `font-normal`. Default changed from `true` to `false` on 2026-07-31: Figma's only concrete reference (a critical "cancelled" banner) renders regular weight, not bold, so that's the safer default absent a confirmed read/unread source for this specific banner. Pressed = `active:brightness-95`.
- **Icon note (2026-07-31):** the "cancelled" type uses a custom SVG (`public/icons/notification-cancelled.svg`, downloaded directly from the Figma node) instead of a `lucide-react` icon, since Figma's `CancelIcon` is a solid/filled glyph that looks meaningfully different from lucide's outline-style `XCircle`. Other types still use `lucide-react` icons (tinted via `tone`) as first-pass placeholders, since Figma provides no reference for them yet — swap to custom SVGs the same way once real examples exist.
- **Open item:** `job_updates.type` → icon mapping slugs in `notificationVisuals.ts` are a first-pass inference (the PRD only gives one literal example, `type: 'delay'`) — confirm/standardize once real `job_updates` rows exist.

- **States:** pressed = `active:scale-[0.96]`.

### `BottomNavigation`
`src/components/shared/BottomNavigation.tsx`

Fixed (sticky), always-visible full navigation bar — not a bottom sheet. Order (right→left, RTL): בית, הזמנות, התראות, פרופיל.

- **Props:** `activeTab` (`home | orders | notifications | profile`), `hasUnreadNotifications?` (boolean - shows the badge; trigger/business logic owned by `/docs/notification_system_prd.md`).

## `components/client/home` — Home Screen-specific

- **`ClientHomeScreen`** — top-level orchestrator (`'use client'`); composes all sections; owns the stubbed click handlers (`console.log` + `TODO` comments) for the not-yet-built Bottom Sheet flows.
- **`SearchSection`** — wraps `SearchBar` + `TimePillsRow`, `gap-6`.
- **`SearchBar`** — controlled text input; only triggers `onSearch` on Enter or clicking the search icon (no auto-search, per PRD 3.3).
- **`TimePillsRow`** — the 2 scheduling entry pills, DOM order "דחוף עכשיו" (first, right) then "לקבוע למועד אחר" (second, left) — matches an isolated Figma node screenshot exactly (verified 2026-07-31; visually non-obvious, don't re-swap without re-checking).
- **`CategorySection`** — heading + row of `CategoryCard`, `justify-between`. Display order for the 4 known categories is fixed via `sortCategoriesForDisplay()` in `src/lib/categoryVisuals.ts` (right→left: electrician, ac, plumber, handyman — matches Figma exactly), **not** `categories.sort_order` from the DB, since the DB's sort_order produces a different order than the design.
- **`PopularServicesSection`** — collapsed (4 pills) / expanded (up to 12 pills) toggle, `flex-wrap justify-start` (packs each wrapped row to the right in this RTL context — see design-system.md "RTL Layout Notes" for why `justify-end` is wrong here). Selection logic in `src/lib/selectPopularServices.ts`: since `services` has no popularity field, uses a deterministic round-robin across categories (ordered by `category.sort_order`) instead of true randomness, so the pill set doesn't reshuffle between renders/expand-toggle.
- **`ServicePill`** — one service pill; background = category color (via the same `resolveCategoryBackground()` used by `ActiveJobCard`/`CategoryCard`), text always `text-brand-primary`.

## `components/client/booking` — Client Booking Flow

- **`BookingFlowSheet`** — single orchestrator overlay for the entire booking flow, opened from Home entry points (first: Search). One continuous flow behind the scenes; swapping the step-content component shown inside the same sheet is purely a UX presentation of that one flow, not separate flows/sheets. Each step component it renders is exactly one "screen" per the Step Screen Reveal Rule (`client-booking-flow-prd.md`) — never two questions on the same screen (see that rule's Authentication exception for why the phone/OTP fields don't count as two questions). Runs match API, then steps through match → (optional message) → scheduling date → scheduling hour (or `no_slots_for_date` instead, if today's 1-hour lead-time cutoff empties the slot list — see `client-booking-flow-prd.md` Step 3) → attachments → authentication (skipped if a session already exists) → new user details (skipped if the verified/known phone already has a profile) → **confirm** (always the final phase, for every path — see `client-booking-flow-prd.md` "Submission"). `confirm` is the only phase that ever renders `OrderRecap` or shows the `"שלח הזמנה"` button; attachments/authentication/new user details always advance via `"הבא"` and never render a recap themselves (fixed 2026-08-21 — an earlier version had attachments/authentication render the recap inline on top of their own content whenever one of them ended up last for a given user, which didn't reliably fit `BottomSheet`'s `max-h-[92dvh]` on every viewport; see `ConfirmStep`'s doc comment). A returning profile's saved addresses/contact-holder name are loaded (`fetchUserAddresses`/`fetchUserBasicProfile`) as soon as a session with an existing profile is known, independent of the phase sequence above; tapping `OrderRecap`'s `"שנה כתובת"` link on `confirm` pushes an extra **`choose_address`** phase (`ChooseAddressStep`) onto the same history stack, `"הקודם"`-reversible like any other phase — see `client-booking-flow-prd.md`'s "Address Book" subsection, added 2026-08-23. `"הקודם"` pops the phase history one entry at a time, **except** a historical `"authentication"` entry once a session already exists — that gets skipped straight through to whatever's under it (confirmed 2026-08-20), since `AuthenticationStep` unmounts/remounts across phase changes (losing its local `phone`/`codeSent`/`code` state) and would otherwise re-render as a blank, unverified-looking phone form for a user who's already verified — the same skip forward navigation already applies once a session exists (see above), so this just makes Previous consistent with it.
- **`SearchMatchStep`** — Figma `OrderBottomSheet_SearchBar`: echo query, category, selectable services + "אין התאמה", price line, Next (enabled after any selection including no-match). The echoed query ("כתבת: ...") is the typo-corrected version returned by the match API, not necessarily the user's raw input — see `client-booking-flow-prd.md`'s Search / AI Matching section.
- **`BookingMessageStep`** — title-styled message + active CTA (`noProfessionals` → back home, shown when the matcher couldn't identify any category at all | `noServiceMatch` → back home (reuses `noProfessionals`'s CTA text rather than duplicating it), shown instead when a category/services WERE identified and shown but the user picked "אין התאמה" - distinct copy ("try rephrasing") since there may well be professionals in the field, just not a matching pill among the ones shown | `noPriceYet` → continues the same flow into Scheduling, heading interpolates the identified category via `categoryLabel` (required for this kind - `SearchMatchStep`, which normally shows "המקצוע המתאים: {category}", is skipped entirely for this outcome, so this is the only screen where that category is ever surfaced) | `noSlotsForDate` → today has no slots left within the 1-hour lead time; explains the latest bookable arrival hour, CTA returns to the Scheduling date screen | `jobCreated` → the Submission confirmation screen ("Flow ends; user sees Job Created confirmation" per client-booking-flow-prd.md "Submission"), CTA closes the sheet back to Home | `submitFailed` → the `submit_booking` RPC call itself failed, CTA retries that same call). `noSlotsForDate` is rendered without `onPrevious` since its CTA already goes back to the date screen — a second button doing the same thing would be redundant.
- **`SchedulingDateStep`** / **`SchedulingHourStep`** — Figma `OrderBottomSheet_Scheduling`: two separate step screens (date question, then hour question), each its own heading/subheading + pill row + Next — the hour screen only renders after the date screen's Next (per the Step Screen Reveal Rule). Selectable day/hour options come from `src/lib/scheduling.ts`, per the business rules in `client-booking-flow-prd.md` Step 3. "היום" always stays selectable on the date screen even once its slots are exhausted (confirmed) — pressing Next with it selected is what routes to `no_slots_for_date` instead of hiding the option pre-emptively.
- **`AttachmentsStep`** — Step 4 (Attachments), visuals per Figma node `8426:6072`: heading + subheading block ("רוצה לדייק את ההזמנה?" / "הוסף תמונות או הערות...") above a single screen (not split per the Step Screen Reveal Rule, since it has no pill-selection question) with two independent, always-visible affordances — "הוסף הערה" and "הוסף תמונות" render as `rounded-full` snackbar-style trigger rows (`bg-surface-notification` + `shadow-notification`, `text-brand-primary` icon, `font-semibold` label — see `design-system.md`'s Bottom Sheet section), not the neutral `bg-surface-pill` used by selectable pills elsewhere in the flow. "הוסף הערה" expands an inline `textarea` below it (`text-text-primary` + `font-normal`, auto-saves to draft on every keystroke, no separate save action; collapses to a same-style rounded-full preview chip with `text-brand-primary` edit (pencil) / delete (trash) icons once filled — icon glyphs shrink to 20px when clustered like this per `design-system.md`'s Icons section, but each still sits in its own 24x24 hit-target box). "הוסף תמונות" opens the native multi-select photo picker, rendering a thumbnail grid (max 3 photos, 16px gap between the button and the grid as well as between thumbnails, each removable via a dark-scrim X — kept high-contrast over arbitrary photo content, not brand-blue) below the button; once 3 photos are selected the trigger disables and switches from `font-semibold text-brand-primary`/`text-primary` to `font-normal text-text-secondary` (icon + label) rather than just fading, plus a `bookingFlow.attachments.maxPhotosReached` note. One `BookingStepFooter` "הבא", always enabled — the whole step is optional. Photos are held as in-memory `File` objects with client-side object-URL previews only (created inside a `useEffect`, not `useMemo`, so React Strict Mode's dev-only double-invoke of effect setup/cleanup on mount can't revoke a freshly-created preview URL before it paints); no Supabase Storage upload is wired yet (see the component's header comment). Both `note` and `photos` are mirrored up to `BookingFlowSheet` on every change (not just on Next) so "הקודם" and back doesn't lose the draft.
- **`AuthenticationStep`** — Step 5 (Authentication). One screen, not two: phone `Input` + `"שלח קוד"` `BookingStepFooter` action; on success, an OTP `Input` reveals inline below the phone field (expand-in-place, same pattern as `AttachmentsStep`'s note field - no navigation to a second screen), with a resend-cooldown control and inline error states (invalid phone, send failure, invalid/expired code). Auto-submits verification as soon as the 6th digit is entered; the footer's action button (labelled per the current sub-state, e.g. `"שלח קוד"` → `"אמת"`) stays as a manual fallback. The phone field is never `disabled`, even once the OTP field appears - it stays editable (and full `text-text-primary`, never fading toward `disabled:opacity-50`) so a typo caught while waiting for the SMS can just be fixed and resent via `"שלח קוד מחדש"` (see design-system.md "Forms"). Never terminal itself: once OTP verifies, the orchestrator advances either to `NewUserDetailsStep` (phone is new) or straight to `ConfirmStep` (phone already has a `public.users` profile) — fixed 2026-08-21, an earlier version re-rendered this screen itself as terminal (`"זיהינו אותך!"` + `OrderRecap` + `"שלח הזמנה"`) for the latter case, see `ConfirmStep`'s doc comment for why that moved out. **No Figma reference yet** — user confirmed frames exist and will provide node IDs; built for now against existing design-system primitives (`Input`, `BookingStepFooter`, the step heading/subheading pattern) pending that visual pass.
- **`AddressFields`** — factored 2026-08-23 out of `NewUserDetailsStep`'s address inputs, so `ChooseAddressStep`'s "add new address" view could reuse the exact same city/street/building-number/apartment/entrance-code layout rather than duplicating it. `showContactFields` (default off) additionally renders a `contactName`/`contactPhone` half-width `Input` row below the address fields — used by `ChooseAddressStep` only (not `NewUserDetailsStep`, which has no UI for contact fields yet — see "Address Book" in `client-booking-flow-prd.md` for why contact fields exist at all). `contactPhone` reuses `formatIsraeliPhoneInput` for display, same as `AuthenticationStep`'s phone field. `disableLocationFields` (added 2026-08-24) locks city/street only — used by `ChooseAddressStep`'s "edit" view, since changing either would mean the saved row now points at a different physical place (see that entry below, and `submit_booking`'s "Edit path" comment in `supabase/sql/address_book.sql`). `contactNameDisabled`/`contactPhoneDisabled` (split from a single `contactFieldsDisabled` on 2026-08-25, after a customer's added contact name silently failed to save because the phone-only value it started with had locked the whole pair) lock each contact field independently — the "edit" view sets each only once *that specific field* already has a value on the address being edited, so a still-blank half stays fillable even if the other one is already set; the "add new" view never sets either.
- **`NewUserDetailsStep`** — Step 6 (New User Details), shown only for a genuinely new phone. One screen, all fields at once (not split per-question like Scheduling, since these are one cohesive "who/where" question, not independent decisions): first/last name `Input`s in one half-width row, then `AddressFields` for city/street/building number/apartment/entrance code (city sits alone on its own full-width row since street's options depend on it; street pairs with building number since "street + number" is filled as one address unit — see `AddressFields` above for the shared layout, and `src/lib/addresses.ts`'s doc comment for why city/street are restricted `Combobox` selections rather than free text). Never terminal: always advances via `"הבא"` to `ConfirmStep` — this screen's own field list already fills the viewport, so it never also renders `OrderRecap` on top of itself. `initialValues` prop repopulates the form when returning via `"הקודם"` from `ConfirmStep`. **No Figma reference yet** — same status as `AuthenticationStep` above.
- **`ChooseAddressStep`** — added 2026-08-23, reached only from `OrderRecap`'s `"שנה כתובת"` link (returning profile only — a brand-new profile has no saved addresses yet to choose between). One component, three internal views (same pattern `AuthenticationStep` uses for phone vs. OTP, not separate step components): a list of every saved address (`fetchUserAddresses`, most-recently-used first) plus an "הוסף כתובת חדשה" row, an "add new" view (the same `AddressFields` with `showContactFields` `NewUserDetailsStep` uses), and an "edit" view (added 2026-08-24). **Select-then-confirm list (reworked 2026-08-25, replacing an earlier "tap a row → immediately exit" design):** tapping an existing row only stages it locally (`stagedSelectionId`/`effectiveStagedSelectionId`, marked with the leading checkmark) — a `BookingStepFooter` with `nextLabel="המשך לביצוע ההזמנה"` (disabled while nothing's staged) is what actually calls `onChooseExisting` and returns to `ConfirmStep`, matching the "select, then press the bottom CTA" pattern every other step in this sheet uses. Saving a brand-new address is the one exception and still exits straight to `ConfirmStep` in one action (nothing else on that screen left to reconsider once a whole new address has just been typed); nothing is persisted to the database until the final `"שלח הזמנה"` tap either way. Each row also has its own `"ערוך"` text link (styled exactly like `OrderRecap`'s `"שנה כתובת"` — `text-xs font-medium text-brand-primary`, `hover:opacity-70`) opening the "edit" view for that address, prefilled and with `disableLocationFields` — `buildingNumber`/`apartment`/`entranceCode` are always editable; city/street stay disabled since changing them is a move, handled by adding a new address instead; `contactNameDisabled`/`contactPhoneDisabled` (independent as of 2026-08-25 — see `AddressFields` above) lock each contact field only once that specific field already has a value, so a still-blank half (e.g. a phone-only contact's missing name) stays fillable (see `submit_booking`'s "Edit path" comment in `supabase/sql/address_book.sql` for the full reasoning, including how this keeps `MAX_OTHER_CONTACT_ADDRESSES` a real cap). The edit view's footer (reworked 2026-08-25) is a `BookingStepFooter` pair — `"חזור"` (via the footer's new `previousLabel` override, discards the in-progress edit) and `"עדכן כתובת"` (commits via `onSaveEdit`) — both returning to the list view locally (`setMode("list")`), never straight back to `ConfirmStep`, so the list stays the one place a selection is actually confirmed. Each row also has a `Trash2` delete icon (added 2026-08-25, hidden when it's the only remaining address) next to "ערוך" — tapping it swaps that row's actions for an inline `"מחק"`/`"ביטול"` confirmation (no separate screen); confirming calls `onDeleteAddress` (soft-delete via the `delete_address` RPC — see "Address Book" in `client-booking-flow-prd.md`), which refreshes the list/usage counts/default in place. List-view rows use `rounded-full` for every row (including two-line "has a contact" rows) and the "add new" row, inside an outer `rounded-card` (24px) container (reverted 2026-08-25 from a brief `rounded-full` outer container), and lead with the selected-checkmark before the address text (reading right-to-left, its natural position) rather than trailing it.
