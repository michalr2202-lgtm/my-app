## Typography

- Font family: **Rubik** (Google Font, self-hosted via `next/font/google`), subsets `latin` + `hebrew`, weights `400/500/600`.
- Line height: **140%** on all in-app typography (`leading-[1.4]`, also set as the `body` default).
- Type scale (matches Tailwind's default scale exactly — no custom `--text-*` tokens needed):

| Tailwind class | Size | Weight used | Example usage |
|---|---|---|---|
| `text-lg` | 18px | `font-semibold` (600) | Section headings, ActiveJobCard category name |
| `text-base` | 16px | `font-normal` (400) | SearchBar input/placeholder |
| `text-sm` | 14px | 400 / 500 / 600 | Body text, pill labels, ActiveJobCard rows |
| `text-xs` | 12px | `font-normal` (400) | BottomNavigation labels |

- **Letter spacing (confirmed 2026-07-31): default is `0` for all typography, set once, globally, on `body` (`letter-spacing: 0` in `globals.css`).** Do not add per-element `tracking-[...]` overrides — an earlier version of this screen copied Figma's per-text-node tracking values (`-0.54px`, `-0.14px`, `0.21px`) directly as local overrides on `ActiveJobCard`, `Pill`, `StatusBar`, and `CategoryCard`; those were auto-kerning artifacts, not intentional tokens, and have been removed in favor of this single global default.
- **Numbers/times must always render left-to-right, even embedded inside an RTL Hebrew sentence** - confirmed as a general rule 2026-09-08. Two sub-cases, depending on whether the numeric content is its own element or sits mid-sentence:
  - **Standalone numeric string** (its own `<p>`/element, e.g. a currency line or time window): give that element `dir="ltr"` directly, even inside an RTL container - prevents the Unicode bidi algorithm from reordering symbols/digits (e.g. `₪ 500-800`). See `OrderCard.tsx`/`OrderRecap.tsx`.
  - **Numeric range embedded mid-sentence** (e.g. `"טווח מחיר עבור עבודה זו: {min}–{max} ₪"`): `dir="ltr"` can't be applied to the whole sentence (it would flip the surrounding Hebrew text too). Bug found 2026-09-08 in `formatServicePriceLine` (`SearchMatchStep`/`CategoryServiceStep`/`ServiceConfirmStep`) - the bidi algorithm was free to reorder `{min}`/`{max}` around the en-dash between them (e.g. showing `300–200` instead of `200–300`). Fix: wrap just the digit-dash-digit run in a Unicode LTR isolate (`\u2066` before, `\u2069` after) - forces correct order without an extra DOM element and without affecting the Hebrew around it. See `servicePricing.ts`.
  - Not every embedded number needs either treatment - a lone number with no second adjacent number (e.g. `"{count} תמונות מצורפות"`), or two numbers separated by a period/colon (e.g. `formatJobDate`'s `dd.mm`, `formatTimeWindow`'s `hh:mm`) are already safe: per the Unicode bidi algorithm's W4 rule, a single European separator (`.`/`:`/plain `-`) between two numbers merges them into one number token, which can't be internally reordered. The bug only appears with **two separate numbers flanking an en-dash (`–`) or other neutral punctuation** with no merging rule - audit any new interpolated-number copy string against this before assuming it's safe.
- **Step heading + subheading pair** (Bottom Sheet step screens, e.g. `SchedulingDateStep`, `AttachmentsStep`): heading `text-lg font-semibold` (18px/600) directly above a subheading `text-sm` (14px/400, `text-text-secondary`), always with exactly `gap-2` (8px) between them in a `flex flex-col` wrapper - a fixed pairing, not decided per-screen.

## Spacing & Radius

- Spacing follows Tailwind's default 4px scale throughout (all Figma pixel values converted directly: 24px → `6`, 16px → `4`, 20px → `5`, 12px → `3`, 8px → `2`, etc.) — no custom `--spacing-*` tokens were needed.
- **Every gap/padding value in this file's Figma is a multiple of 4px, down to a 2px minimum** (`gap-0.5`) for the tightest icon clusters - never an arbitrary odd pixel value. When implementing a new screen, match Figma's exact spacing via this scale rather than eyeballing it; if a Figma value doesn't cleanly land on 2/4/8/12/16/20/24…, re-measure rather than assuming it's a new, smaller-than-2px increment.
- `--radius-card: 24px` → `rounded-card`, used for `Card` (ActiveJobCard) and Bottom Sheet top corners (`rounded-t-card`).
- All pill-shaped elements use `rounded-full` (Figma uses both `99px` and `44px` radii for different pills — visually indistinguishable at these heights, so unified to `rounded-full`).

## Bottom Sheet

Shared overlay pattern for the Client Booking Flow (and future multi-step sheets).

- **Scrim:** full viewport `bg-overlay-scrim` (70% black). Tap dismisses the sheet (same as close). Covers Bottom Navigation.
- **Panel:** docks to the bottom of the centered mobile shell (`max-w-[480px]`), white `bg-surface-bg`, top corners `rounded-t-card` (24px), horizontal padding 16px, top 16px / bottom 24px. Capped at `max-h-[92dvh]` with `overflow-y-auto` as a defensive fallback only - **no screen may ever actually scroll**, on any device (confirmed 2026-08-21). Every step is independently sized to fit within that cap; a step that wouldn't fit is split into an additional screen instead of relying on this scroll (`NewUserDetailsStep`, the tallest, was deliberately kept recap-free for exactly this reason, and the shared `ConfirmStep` exists so no step ever needs to combine its own content with the order recap - see `BottomSheet.tsx`'s doc comment).
- **Close control:** 24px X (lucide), top-**left** visually (`justify-end` in RTL flex so the control sits on the physical left, matching Figma), press scale per global small-element rules.
- **Step content:** one step visible at a time; advancing replaces content (do not stack long multi-question scroll for the full flow).
- **Selectable service pills (booking):** uniform `bg-surface-pill` + `text-text-secondary`; selected = `bg-surface-selected` + `text-text-secondary`. Not the same as Home `ServicePill` (category-colored).
- **`sheetNext` button:** full width, `rounded-full`, `text-base font-medium`, py 15 / px 22.5.
  - Inactive (no selection / disabled): `bg-surface-pill` + `text-text-secondary`
  - Active (enabled after selection): `bg-surface-selected` + `text-brand-primary`
  - Press: same global `active:scale-[0.96] active:brightness-95` as other CTAs
- **Snackbar-style action trigger (`AttachmentsStep`):** a step can offer optional in-place actions (e.g. "הוסף הערה", "הוסף תמונות") as full-width `rounded-full` rows using `bg-surface-notification` + `shadow-notification` + `text-brand-primary` icon, instead of the neutral `bg-surface-pill` used by selectable pills above — this is a *trigger*, not a selectable choice, so it borrows the lighter/elevated NotificationBanner look to read as "tap to act" rather than "pick one of these options."
  - Disabled (e.g. "הוסף תמונות" once the 3-photo max is reached): icon + label switch color only, `text-brand-primary` → `text-text-secondary` (a deliberate color change rather than opacity, matching how `sheetNext` above also uses a distinct color pairing for its inactive state instead of fading the active one) — **font weight never changes between a trigger's active/disabled states** (confirmed 2026-09-03; briefly also dropped from `font-medium` to `font-normal` on disable, which read as two unrelated changes happening at once instead of one clean "now unavailable" signal). Any other trigger that later gains a disabled state follows this same weight-stays/color-changes rule.
- **"Snackbar but Cooler" pill family - three variants sharing one shape** (`rounded-full`, `px-6 py-3`, `gap-3` when it has more than one child), formalized 2026-09-04 once `ChooseAddressStep`'s redesigned address rows became this shape's second consumer, not a one-off `AttachmentsStep` treatment. Same box in every variant — only the border/background/shadow (and, for plain, the text weight) change, so switching between them (e.g. a row going from unselected to selected) never causes any padding/height/tap-target shift:
  - **Filled** (default/unselected state - `AttachmentsStep`'s triggers, `ChooseAddressStep`'s unselected address rows): `bg-surface-notification` + `shadow-notification`, no border.
  - **Outlined** (an actively-selected choice - `ChooseAddressStep`'s selected address row, confirmed 2026-09-04 replacing an earlier leading-checkmark treatment): `border border-brand-primary`, no background, no shadow — a selected row deliberately reads as "lighter"/less chrome than an unselected one, not more.
  - **Plain** (a same-shaped trigger with no chrome at all - `ChooseAddressStep`'s "הוסף כתובת חדשה"): no border, no background, no shadow — just `text-brand-primary font-semibold` text inside the same `rounded-full`/`px-6 py-3` box. Still gets the full box (not a bare text link) purely so its tap target and vertical rhythm match its Filled/Outlined siblings exactly, even though nothing about it looks like a "card."
  Don't add a fourth variant or a new shape for the next "pill row" need without checking whether it's actually one of these three first.
- **This is a distinct shape/component from the shared `Pill` primitive** (`rounded-full`, `px-4 py-3` - smaller horizontal padding than this family's `px-6`) even though both went background-less the same day (2026-09-04) for the same underlying reason ("a secondary action reads clearly enough from its text color alone, no fill needed"). `Pill` backs Home's "דחוף עכשיו"/"לקבוע למועד אחר" (`TimePillsRow`) and "הצג יותר עבודות"/"הצג פחות" (`PopularServicesSection`), plus `OrderRecap`'s "שנה כתובת" - see `Pill.tsx`'s own doc comment for that change. Don't merge the two into one component just because they're both "text-only secondary buttons" now - they're different sizes or reused in genuinely different contexts (a row that can also hold a leading icon/gap vs. a bare standalone button), and Home's `Pill` usages predate this whole "Snackbar but Cooler" family by weeks.

## Forms

- **Text field (`Input`):** `rounded-xl border border-divider`, `px-4 py-3`, focus = `border-brand-primary`. First introduced for `AuthenticationStep`/`NewUserDetailsStep` - the first real form fields in the app beyond `AttachmentsStep`'s note `textarea`.
- **Typed value color (confirmed 2026-08-19): `text-text-primary`** (black), always - once real, committed content, never faded/muted regardless of context, including inside a Bottom Sheet. Considered and rejected: matching `SearchBar`'s typed-text color (`text-text-secondary`, gray) for consistency with that "in a sheet/overlay" context - rejected because `SearchBar`'s gray is a narrower, deliberate choice for that one component (a softer look for a discovery/search affordance), not a general "text inside an overlay is muted" rule, and these Bottom Sheet fields are the opposite case: phone numbers, OTP codes, and addresses are exactly the kind of content where a misread digit has real consequences (no SMS delivered, professional can't find the address), so they need the highest-contrast color available, same as anywhere else in the app.
  - **Exception - a genuinely locked field (confirmed 2026-09-03):** `ChooseAddressStep`'s edit view fades a field's already-typed value to `disabled:opacity-50` once that specific value has actually gone out in a submitted job (see `Address`'s `*_locked` columns, `supabase/sql/address_book.sql`) - the opposite call from the phone-field case just below, and a deliberate, narrow carve-out from "never faded/muted regardless of context" above. The two situations look similar (both are a filled `Input`) but aren't: the phone field is only *temporarily* not the thing to edit right now (still perfectly editable, nothing to warn about), while a locked address field can genuinely *never* be edited again through this screen at all - without some visible difference from its still-editable neighbors, a customer scanning the form for "what can I still fix" would have no way to tell short of tapping every field one by one. Full-opacity-even-when-locked was tried first and reverted the same day once this became clear in practice.
- **Placeholder/alternate text color (confirmed 2026-08-19): `text-text-secondary/20`** (`text-secondary` at 20% opacity) for a labeled field, plain full-opacity `text-text-secondary` for an unlabeled one - see "Labeled vs. unlabeled placeholders" below for why the two need different treatment. Applies both to every native `placeholder` (`Input`, `Combobox`'s searchable variant) and to `Combobox`'s closed-state "nothing selected yet" label, which visually serves the same role even though it's not a native `placeholder` attribute - both components pick the color automatically based on whether their own `label` prop is set, so callers never choose it directly.
  - **Labeled vs. unlabeled placeholders:** a field with a visible `label` above it (`Input`/`Combobox` everywhere they're currently used - `AuthenticationStep`, `NewUserDetailsStep`) can afford a very faint placeholder, since the label already names the field - the placeholder there is only a supplementary format hint, not the sole instruction. A field with **no** label above it - `SearchBar`'s bespoke input (no `Input`/label at all, just the placeholder itself, e.g. `"איזו תקלה יש לך בבית היום?"`) and `AttachmentsStep`'s note `textarea` (expands with no label of its own once "הוסף הערה" is tapped) - keeps the placeholder at full `text-secondary`: it's the only thing telling the user what to type, so fading it to near-invisibility would hurt usability rather than just being a style choice. Don't fade these to `/20` even though they're visually "placeholder text" too.
  - **Placeholder policy (labeled fields):** only add a placeholder where the field's *expected format* isn't obvious from its label/input mode alone (e.g. the phone field's `"050-1234567"` example - local Israeli numbers are commonly written with or without the dash, so showing the expected shape removes ambiguity). Don't add "example value" placeholders to fields that are already self-explanatory from their label (`NewUserDetailsStep`'s name/building-number/apartment/entrance-code fields all deliberately have none) - they'd just be extra visual noise, and (per the fix below) a placeholder that's a plausible-looking example is easy to mistake for a real value.
  - **Phone field, specifically:** in addition to the fainter color, its placeholder also fades out immediately on focus (`focus:placeholder:opacity-0`, transition matching `SearchBar`'s existing fade), not just once typing starts (native placeholder behavior) - a `"050-1234567"`-shaped example is realistic enough looking that users could otherwise mistake it for an already-filled, undeletable value. The field also formats digits as the user types (dash inserted after the 3-digit prefix, via `formatIsraeliPhoneInput` in `src/lib/phone.ts`) so what's typed always matches that same placeholder shape. A single formatted field was chosen over splitting the prefix into its own dropdown - Israelis type their own number as one habitual sequence, and a prefix dropdown (there are ~8 valid mobile prefixes) would add a tap most users don't need for something typed this often.
  - **Phone field stays editable after a code's sent (confirmed 2026-08-20):** it's never `disabled`, even once the OTP field appears below it - a typo is only obvious once you're staring at a code that'll never arrive, so locking the field at exactly that moment was wrong, and `Input`'s `disabled:opacity-50` was also fading the already-typed number for no real reason (typed content should stay full `text-text-primary` per "Typed value color" above, disabled or not). Editing it doesn't resend anything on its own; `"שלח קוד מחדש"` reads the same live `phone` value, so fixing a typo and tapping resend just works.
- **Field error state:** border switches to `border-notification-red`; error text below the field also uses `text-notification-red` at `text-xs`. This reuses the existing notification-red token (previously only the unread badge/"problem" tone) rather than introducing a new error color - a field error and a "problem" notification are the same semantic meaning (something needs the user's attention).
- **Helper/error text:** `text-xs`, positioned directly below the field, `text-text-secondary` for helper text or `text-notification-red` for an error (error takes precedence when both would apply).
- **Two-field row (half-width fields):** `flex w-full gap-3` wrapper, each field `flex-1` - used for name, and apartment/entrance-code pairs in `NewUserDetailsStep`. Not a `grid`; matches the app's flex-first layout convention.
- **Uneven two-field row (street + building number):** same `flex w-full gap-3` wrapper, but street `Combobox` is `min-w-0 flex-1` (takes essentially the whole row) and building number `Input` is a fixed `w-[72px] flex-none` (not a flex share) - street names need real room (some run 15-19 characters) while a building number is 1-3 digits, about as much room as a `Pill` needs, so giving it a proportional flex share would still be more space than it ever uses at the street field's expense. Street and building number share a row (not street and city) because "street + number" is filled as one address unit (e.g. "הרצל 15"); city gets its own full-width row above instead, since it's a prerequisite the street field is disabled on, not a peer of it.
- **`className` targets the outer wrapper, not the `<input>` (confirmed 2026-08-19):** both `Input` and `Combobox` apply their `className` prop to the field's outer wrapper `<div>` - the element that's actually the flex item in a parent row - so layout classes (`flex-1`, `w-[72px]`, ...) size the field correctly. `Input` has a separate `inputClassName` for the rarer case of styling the `<input>` tag itself (e.g. a `focus:placeholder:` pseudo-class override, see the phone field above) - `Combobox` has no `<input>`-equivalent escape hatch since it only ever renders a plain `<button>`/filter `<input>` internally. Before this split, `Input`'s `className` landed on the inner `<input>` (a flex item in a *column* along with the label/helper text, so `flex-1`/`w-[72px]` from an outer *row* had no effect on width) while `Combobox`'s already landed on its wrapper - the inconsistency was the root cause of a real bug: the street/building-number row rendering backwards, with the un-sized `Input` wrapper claiming nearly the whole row and the correctly-flexed `Combobox` getting squeezed to almost nothing.
- **`cn()` uses `tailwind-merge` (confirmed 2026-08-19), not plain string concatenation:** `src/lib/cn.ts` is `twMerge(clsx(...))` - when a component's own base classes and a caller's `className` set the *same* CSS property (e.g. `Input`'s base `w-full` vs. a caller's `w-[72px]`), `twMerge` resolves the conflict by property, always letting the later argument win, matching what a developer reading `cn(base, className)` would expect. Plain concatenation (the original implementation) instead left the winner dependent on Tailwind's internal generation order in the compiled stylesheet - unrelated to argument order - which is what actually broke the street/building-number row after the `className`-target fix above: both `w-full` (base) and `w-[72px]` (caller) landed in the stylesheet, and the wrong one happened to win, so the row rendered stacked/overlapping instead of side-by-side until `twMerge` was added.
- **Mobile tap/autofill chrome neutralized globally (confirmed 2026-08-19):** `globals.css` sets `-webkit-tap-highlight-color: transparent` on `html` (suppresses the browser's own translucent tap-flash overlay, since every interactive element already has its own deliberate `active:` press feedback) and overrides `input:-webkit-autofill`'s forced background tint via a `1000px` inset `box-shadow` (the standard technique, since a plain `background-color` rule can't out-rank the browser's own autofill styling) - fixes the phone field's background intermittently flashing light blue when a browser offers to autofill a saved/suggested number. Phone (`autoComplete="tel"`), OTP code (`autoComplete="one-time-code"` - also enables native SMS-code autofill on supporting browsers), and name fields (`autoComplete="given-name"`/`"family-name"`) all set the correct semantic `autoComplete` token too, both for correctness and so the browser doesn't have to guess.
- **Restricted select (`Combobox`):** same box styling as `Input`, plus a chevron icon; opening it expands its option list inline below the field, in normal flow (not a floating/absolute panel) - consistent with the "expand-in-place" pattern used elsewhere (OTP field, attachments note). A selected value that's too long for the field's width truncates with an ellipsis rather than breaking the layout; the option list itself never truncates a label, wrapping to a second line instead, so the full value is always readable while choosing. For long option lists (e.g. `NewUserDetailsStep`'s street field, ~700+ entries), the list only renders once the user has typed at least one character, showing a hint in its place until then - both to avoid mounting hundreds of DOM nodes unprompted and because typing-to-narrow is the expected interaction for a list that size.

## RTL Layout Notes

**Critical gotcha (found during 2026-07-31 visual QA):** in a native `dir="rtl"` flex row (`flex-direction: row` under `direction: rtl`), CSS `justify-content: flex-end` (Tailwind `justify-end`) packs content to the **left**, not the right — because "end" follows the inline-direction end of the writing mode, and RTL's inline end is the left. To pack a row flush against the right edge (the visually-intuitive "RTL-aligned" result), use `justify-start` (Tailwind `justify-start`, or omit the class — it's the default) instead. This bit `PopularServicesSection`'s `ServiceGrid`, which used `justify-end` and ended up packed left with a gap on the right.

This project does **not** use Figma's exported `-scale-y-100 rotate-180` mirror-transform hack for RTL (that's a code-gen artifact for simulating RTL from an LTR-authored canvas, produced by some Figma exports) — components here are built RTL-native (`dir="rtl"` inherited from `<html>`, first DOM child = right). When verifying order/position against Figma, don't trust `get_metadata`'s raw x-coordinates blindly either — cross-check with an isolated `get_screenshot` of the specific node, since not all elements in this file are authored/flipped consistently (e.g. `SearchBar`'s internal layout is mirrored relative to its raw metadata, while `CategorySection`/`TimePillsRow`/`ServiceGrid` are not).

**Asymmetric padding gotcha (`NotificationBanner`, resolved 2026-08-02 after 3 attempts):** don't trust `get_design_context`'s raw `pl-[…]`/`pr-[…]` class names OR `get_metadata`'s per-node `width` at face value for this file — both can be misleading. Two failure modes hit here:
1. **Element order:** the raw JSX order (icon, then text) does NOT reliably tell you left/right without checking - this file mixes mirrored and non-mirrored components (see above). Confirmed by direct pixel measurement (downloading the exported PNG and scanning pixel columns) that the icon renders on the **right** and text on the **left** here, opposite of the initial guess.
2. **Padding split:** `get_metadata`'s text-node `width` (e.g. `275px`) is the node's authored **box** width, not its rendered ink width (Hebrew text can be short and right-aligned inside a much wider fixed box) - don't plug it into a `pl + icon + gap + text + pr = containerWidth` equation assuming ink-width == box-width; both `pl+pr` combinations can satisfy that sum, so the arithmetic alone doesn't tell you which side is bigger. The reliable method: download the actual rendered PNG (`get_screenshot`) and measure real pixel positions of the icon and text ink directly (e.g. a small script scanning columns for reddish vs. dark-gray pixels) - only that settled it (icon's right edge lands exactly `24px` from the container's right edge; the text's fixed box starts exactly `12px` from the left edge).

## Icons

- **Standard size: 24×24px, literal `size={24}` directly on the `lucide-react` icon** (`strokeWidth={1.75}`, no separate wrapper, no smaller glyph inside a bigger box) - e.g. `NotificationBanner`'s tone icon, `SearchBar`'s search icon, `BottomSheet`'s close X, `AttachmentsStep`'s `StickyNote`/`Image`/`Pencil`/`Trash2`. This is a fixed app-wide constant, not per-component - don't pick an arbitrary size per usage. **Confirmed 2026-09-03:** a same-day attempt to shrink these same four `AttachmentsStep` icons to a 16px glyph inside a 24px box (reasoning: different Figma icon libraries bake different amounts of padding into their own exported artwork, so matching one library's proportions literally shrank the others) was tried and reverted the same day - in practice it just read as "the icons got smaller", the opposite of matching Figma at a confident 24px. `lucide-react` is this app's one global icon set specifically so this kind of per-icon fidelity chase isn't needed - pick the closest-matching glyph and render it at the standard size, full stop.
- **Sourcing policy (standing rule, confirmed 2026-09-29): default to `lucide-react`, never a custom Figma-downloaded SVG, unless the customer explicitly says otherwise for that specific icon.** This matters even when a Figma node ships its own icon asset - a Figma reference showing a custom SVG is not, by itself, a reason to download and use that SVG; `lucide-react`'s closest equivalent is the default every time (lighter bundle, one consistent icon set, the direction this app is deliberately going). The one standing exception remains `notification-cancelled.svg` below (Figma's filled `CancelIcon` looks meaningfully different from lucide's outline `XCircle` - a real visual mismatch, decided case-by-case, not a general license to prefer custom assets). Concrete failure mode this rule now prevents: `JobDetailsScreen`'s call button was first built with a custom-downloaded `phone-call.svg` (Figma node `9141:6139`) purely because that's what the Figma node happened to contain, then corrected to lucide's `Phone` the same day once flagged - lucide already had a perfectly good equivalent that should have been used from the start.
- **Position: always 24px padding from the nearest edge of its row**, matching whichever side it sits on - `pr-6` when the icon leads a RTL row (first DOM child - e.g. `NotificationBanner`, `AttachmentsStep` triggers), `pl-6` (via the container's `px-6`) when it trails (e.g. `SearchBar`'s search button is the last child, landing 24px from the left). This padding must stay the container's padding, not padding baked into the icon's own wrapper, so it lines up exactly whether there's an icon, a cluster of icons, or a different icon swapped in later.
- **Row height stability:** because the icon's box height plus the row's vertical padding determines the row's total height, keep both the icon size and vertical padding (`py-3` for snackbar-style rows) identical across a component's different states - e.g. `AttachmentsStep`'s "הוסף הערה" trigger and its filled/collapsed note chip must render at the same height, so the row doesn't visibly grow or shrink when its content changes. This only stops applying once a state genuinely needs a second line of content (multi-line text), which is a separate, deliberate exception, not a sign the single-line rule was wrong.
- **Two+ icons in one row (e.g. `AttachmentsStep`'s filled note chip - edit + delete trailing the note text) are `gap-3` (12px) apart** - the same gap already used between the row's other elements (text ↔ icon), not a tighter `gap-1`-style clustering; each icon stays the standard full 24px regardless of how many are in the row.
- **Row padding is symmetric (`px-6`, 24px each side) once the row leads with text instead of an icon** - the filled note chip above is the example: with no single icon anymore claiming "the leading edge", both edges get the full 24px for balance, rather than carrying over the *icon-leads* trigger row's asymmetric `pr-6`/`pl-3` (see "Position" above) unchanged. The same reasoning applies to `AttachmentsStep`'s note `textarea` (confirmed 2026-09-03) - also a bare text field with no icon at all, so it gets the same symmetric `px-6`, not the `px-4` an isolated text field might otherwise default to.
- **Exception - badges layered over unrelated content** (e.g. the delete-X on an `AttachmentsStep` photo thumbnail): a distinct, smaller pattern (12-16px), positioned with a small fixed inset from the corner of the thing it overlays (not the 24px row-edge rule) - it's an overlay indicator on top of arbitrary content (a photo), not a standard row icon, and needs guaranteed contrast (dark scrim background) that a row icon doesn't.

## Interaction & Motion

Per the global interaction rules:

- Transition: `transition-all duration-200 ease-[cubic-bezier(0.4,0,0.2,1)]` on all interactive elements.
- Small elements (Pill, CategoryCard icon): `active:scale-[0.96]`.
- Large elements (Card): no scaling — background darkens instead.
- Background darkening on press ("10% darker"): implemented as `active:brightness-95` rather than a literal `[name]-active` hex token per color. This is a deliberate deviation from the literal "define an -active token per color" rule, because several backgrounds here are **data-driven** (arbitrary hex from the DB, e.g. a professional's category color that isn't one of the 4 fixed tokens) — a `brightness` filter darkens any background uniformly without needing to precompute a darker variant for every possible value. Fixed-token colors (pills, categories) could still get literal `-active` tokens later if a case arises where `brightness` isn't visually sufficient.
- Bottom Navigation: no scale/shadow/background change — only icon + label color change (`text-text-secondary` → `text-brand-primary`).
- Notification badge: solid `bg-notification-red` dot, absolutely positioned over the Notifications tab icon only (Client App — Orders tab never shows a badge).
- **Overlay entrance (added 2026-09-28, `ImageLightbox`):** an opening overlay whose whole point is a quiet, deliberate moment (as opposed to Bottom Sheet's quick utilitarian slide) fades its scrim in over 300ms `ease-out` while its content fades in *and* scales from 95%→100% over 350ms `cubic-bezier(0.16,1,0.3,1)` - a fast-start/soft-landing curve, distinct from the global 200ms press-feedback easing above. See `ImageLightbox.tsx`'s doc comment for the exact implementation (a manual `entered` flag flipped via `requestAnimationFrame`, since CSS transitions need two separately-painted frames to animate between).
