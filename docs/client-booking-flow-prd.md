# PRD – Client Booking Flow (Bottom Sheet)

## Screen Description

This document describes the shared, multi-step Bottom Sheet flow that collects the information required to create a Job (Order).

It is entered from multiple buttons across the Client app (currently: the Home Screen), and defines:

- the single canonical step sequence
- how each entry point maps onto that sequence (starting step + pre-filled/skipped steps)
- what information each step collects
- which Order section each step's data belongs to
- flow-level states and edge cases

This is a **draft** produced from existing approved documentation (`project-prd.md`, `home-screen-prd.md`, `order-model.md`) plus confirmed product decisions from review. Sections marked **Needs Confirmation** still require a decision before implementation of those specific pieces begins.

Visual implementation (once approved) must follow Figma exactly, as usual. This document defines business/flow behavior only - not visual design.

## 1. Goal

Enable a customer to go from any entry point (free-text search, urgency selection, category, or specific service) to a created Job, through the shortest path possible given what is already known at the entry point - without ever re-asking a question the user has effectively already answered.

Per `home-screen-prd.md` Rule 1: **all entry points open a Bottom Sheet.** This document defines what that Bottom Sheet actually is: one flow, reused everywhere.

---

## 2. Master Step Sequence

This is the full path, as if entering with zero prior context. Every entry point is a shortcut into this same sequence - never a different flow.

Confirmed order:

1. Category Selection
2. Service Selection
3. Scheduling
4. Attachments (Photos / Notes) — optional to fill
5. Authentication (phone + OTP) — only if no active session
6. New User Details — only if the verified phone is new
7. Confirm — always the final screen, for every path

Step 7 is the one shared "Confirm & Submit" screen for every path (fixed 2026-08-21 - see "Submission" below for why this replaced an earlier design where Steps 4/5 could themselves be terminal). Steps 4-6 never render a submit button or an order recap themselves; they always advance via `"הבא"` to Step 7.

### Step 1: Category Selection

- Shown when the target category is not yet known.
- User selects a category.
- Advances to Step 2.
- **Implemented 2026-09-06** as `CategoryStep`, for the Time Pill entry (Flow 2) - one of the 4 fixed Home Screen categories, shown as pills (no "אין התאמה" option here, unlike Step 2's AI-search variant - category is picked directly, never inferred). For "דחוף עכשיו" specifically, this same screen additionally shows an urgency-framing block above the category question (`urgentNow.heading`/`.subtext`, reusing the existing "Now" flow's SLA wording rather than inventing new numbers - see `project-prd.md` §5 "Immediate ('Now') Job Matching"); "לקבוע למועד אחר" reaches the identical screen with that block omitted.

### Step 2: Service Selection

- Shown when the target service is not yet known.
- Shows services within the resolved category (or, coming from AI matching, up to 3 suggested services - see Entry Point Mapping / Search).
- User selects a service, and quantity if relevant (per `project-prd.md` Step 3).
- Displays price range from the catalog, or "price after inspection" for diagnosis-type pricing.
- Advances to Step 3.
- **Implemented 2026-09-06** as `CategoryServiceStep`, for the Time Pill entry (Flow 2) only - shows every active catalog service in the Step 1-picked category (currently always exactly 10 per category; confirmed against live data, so there's no ranking/truncation logic to design here, unlike a true "top N" scenario). Includes an "אחר / לא מוצא את מה שאני מחפש" pill - **reworked the same day** from an immediate jump to a message screen into a free-text field: tapping it swaps the pill for a `NoteField` (the same textarea/chip object `AttachmentsStep`'s note uses); "הבא" then runs that typed description through the *exact same AI classification* `SearchMatchStep`'s search-box entry uses (`handleCategoryOtherNext`/`/api/ai/match-services`), landing on whichever of that outcome's three screens applies - `SearchMatchStep` itself (services found - possibly in a *different* category than Step 1's pick, flagged via a swapped-in heading, see below), the "category known without priced service" message (`noPriceYet` - always this wording now, never a separately-worded variant, since the category is AI-identified from typed text here too, not directly chosen), or "no professionals in this field" - rather than deciding the outcome from the fixed category alone. When `SearchMatchStep` is reached this way, its usual "נראה שהבנו את הבעיה" / "כתבת: '...'" heading pair is swapped for "השירות שביקשת" + the raw typed text (no quoting), and its "המקצוע המתאים:" profession line is shown only if the AI's classification actually disagrees with Step 1's pick (worded "המקצוע המתאים על פי מה שתיארת:" in that case) - skipped entirely when it agrees, since re-announcing an unchanged category would be redundant.
- **Implemented 2026-09-07** as a second, lightweight `ServiceConfirmStep` variant ("Step 2.5"), for the Service Pill entry (Flow 4) only - the exact service is already known here (the Popular Services pill tapped), so there is no pill grid to show or select from at all, just a confirmation display: the chosen service + its price first, then its category ("המקצוע המתאים:", reusing `SearchMatchStep`'s own label - same cross-namespace reuse pattern as the "אחר" field's `professionLabelOverride`). "הבא" advances straight to Step 3, same as every other path.

### Step 3: Scheduling

- A date question followed by a time-slot question (Figma: `OrderBottomSheet_Scheduling`, node `8412:6072`) - two separate screens per Rule 5 (Step Screen Reveal Rule): the hour question only appears after "הבא" is pressed on the date screen. There is no separate "Now vs. later" toggle inside this step - urgency is resolved before reaching it:
  - **Home Screen Time Pill entry (Flow 2, "דחוף עכשיו"):** pre-selects immediate/"Now" and **skips this step entirely** (per Entry Point Mapping below). Matching/arrival deadlines then run after Submission - see `project-prd.md` Section 5 ("Immediate ('Now') Job Matching"). **Implemented 2026-09-06:** mechanically, `selectedDate`/`selectedHour` are simply never set for this path (`CategoryServiceStep`'s "הבא" advances straight to Step 4/Attachments - see `BookingFlowSheet.advanceToScheduling`), so the recap's `scheduledTime` falls back to submission time on its own - no separate "is this an urgent job" flag exists or is needed anywhere, including in `submit_booking`. **Refined 2026-09-07:** that fallback no longer uses the raw, unrounded submission instant (which showed an ugly window like "14:37-15:37") - `scheduling.ts`'s `roundUrgentNowScheduledTime` rounds it UP to the nearest half-hour instead, deliberately never down (a floor could make the displayed window's end land before the real 60-minute arrival guarantee above) and deliberately with no business-hours cap (rounding alone can never cross an hour boundary that the original request time hadn't already crossed, so a cap could only ever clamp a late request *backward* into a window that already looks past - worse than the problem it would solve; "Immediate Now" has no business-hours gate anyway).
  - **Every other entry point** (Search, Category Card, Service Pill) reaches this step and picks a date + time slot, including **today** - selecting today does not require the soonest slot; it books a specific hour later the same day (confirmed: today is a normal, always-available date option, not reserved for the "Now" flow).
- Date range (confirmed):
  - Offer **6 selectable dates**, in calendar order starting from and including today (e.g. if today is Sunday: today, Monday, Tuesday, Wednesday, Thursday, Friday - Saturday is skipped and does not count toward the 6).
  - **Exclude Saturday only** - Friday is a normal selectable day (with shortened hours, see below).
- Time slots (confirmed): **1-hour windows** (per Figma; supersedes the old "2-hour window" assumption - `project-prd.md` Step 4 updated to match).
  - Working hours: **08:00-18:00** on every day except Friday.
  - **Friday: 08:00-14:00** (shortened hours before Shabbat) - last selectable slot is 13:00-14:00.
  - When today is selected, slots are only offered if they start more than **1 hour** from now (confirmed lead time - not just "not yet started"; a professional needs realistic notice to be dispatched).
  - If today's lead-time cutoff empties the slot list entirely (today past its last bookable hour, or today being Friday past its last bookable hour), the hour screen is skipped and a dedicated message screen is shown instead (`BookingMessageStep` kind `noSlotsForDate`): explains that appointments require 1 hour of notice and that the latest bookable arrival hour is 18:00 on weekdays / 14:00 on Fridays (framed as the latest **arrival** time, not "hours of operation" - the job itself may run later than that), with a single "בחר יום אחר" CTA back to the date screen. "היום" itself stays selectable on the date screen regardless (confirmed) - this message is only reached after pressing "הבא" with today chosen.
- Persists to `jobs.scheduled_time` (`timestamptz` - start of the chosen 1-hour window; confirmed against the live schema 2026-08-06 - the column was previously `scheduled_date`/`date`-only and has been migrated).
- Advances to Step 4.

### Step 4: Attachments (Photos / Notes)

- Optional to fill - the customer may skip without adding photos or notes.
- The step itself is always part of the sequence (shown regardless of entry point) unless a future decision says otherwise.
- Maps to the Order's Attachments section (per `order-model.md`: "Images and files related to the Order... may include Customer images").
- **One single screen** (unlike Scheduling) - both affordances below are always visible together from the moment the screen loads. This is a deliberate choice: because notes and photos are independent and both optional, showing both at once avoids ever needing to "ask about photos later" if the user only interacted with notes (or vice versa) - there is exactly one "הבא" for the whole step, always enabled.
  - **Notes:** tapping the "הוסף הערה" row expands an inline text field directly below it (autofocus). The text is saved to the draft automatically on every keystroke - no separate "שמירה" action, consistent with how every other answer in this flow (selected service, date, etc.) is captured immediately rather than behind an explicit save step. Once collapsed with text present, the row shows a truncated preview ("chip") of the note with edit (pencil) and delete (trash) affordances.
  - **Photos:** tapping "הוסף תמונות" opens the native photo picker (camera/gallery, multi-select). Selected photos render as a thumbnail grid directly below the button, each with its own delete (X). **Confirmed: maximum 3 photos** - once reached, the add-photos affordance is disabled/hidden until a photo is removed.
- Always advances via `"הבא"` - never terminal itself. If an active session already exists on this device AND that session's profile is complete, Steps 5-6 are skipped and "הבא" here goes straight to Step 7 (Confirm) instead; otherwise it goes to Step 5. (Fixed 2026-08-21: an earlier version made this screen itself the Submission action - swapping its label to `"שלח הזמנה"` and rendering the read-only order recap alongside the notes/photos content - whenever it was terminal for a given user. That combined layout didn't reliably fit `BottomSheet`'s `max-h-[92dvh]` on every viewport, observed as a scrollbar inside the sheet on a laptop; see Step 7/"Submission" below and `ConfirmStep`'s doc comment.)

### Step 5: Authentication

- Shown only if there is no active session on the current device. Authentication is a **device/session-level** check, not a per-order check - once verified, the user stays authenticated across app opens until they explicitly log out or the local session is cleared (app data deleted / reinstall / new device).
- **One screen, not two:** phone number input, then tapping "שלח קוד" reveals an OTP code field inline on the same screen (expand-in-place, the same pattern `AttachmentsStep` uses for its note field - no navigation to a second screen/history entry). OTP sent via Supabase (per `project-prd.md` Step 5). Auto-verifies as soon as the 6th digit is entered; an "אמת" button stays available as a manual fallback (e.g. pasting the code). A resend control appears after a short cooldown.
- On successful OTP verification, a session is established on the device via Supabase Auth (mechanism detail belongs in `frontend-architecture.md` once implemented).
- Whether the verified phone is new or already known in the `users` table can only be checked **after** verification succeeds (the check is scoped to the now-authenticated identity, per Row Level Security - it can't be answered against an unverified, client-typed number). This determines what happens next - never terminal itself:
  - **Phone already has a profile** (returning customer, even on a new device or after logout/reinstall): advances straight to Step 7 (Confirm) - existing profile data is reused, nothing else is asked. (Fixed 2026-08-21: an earlier version made this screen itself terminal here, re-rendering with a `"זיהינו אותך!"` heading + the recap + a `"שלח הזמנה"` button in place of advancing - moved to the shared Step 7 for consistency with the other two populations, see "Submission" below.)
  - **Phone is new**: advances directly to Step 6, with no intermediate acknowledgment screen - Step 6's own heading (`"רק עוד כמה פרטים"`) already delivers the "almost done" reassurance an interstitial message would otherwise repeat, so adding one would just be redundant dead time before a form the user still has to fill in.
- If a valid session already exists on this device, this step is skipped entirely.

### Step 6: New User Details

- Shown only if the phone number verified in Step 5 does not already exist in the `users` table (i.e., a genuinely new customer - regardless of device history).
- **One screen, all fields at once:** first name, last name, city, street, building number, apartment (optional), entrance code (optional) - per `project-prd.md` Step 5. Phone is not asked here - it was already verified in Step 5.
  - **City and street** are both restricted `Combobox` selections, not free text - per the MVP Geographic Scope in `project-prd.md`, Herzliya and Ramat Hasharon are the only two legal cities, and street is restricted to that city's real, official street registry (sourced from Israel's Population and Immigration Authority via data.gov.il - see `src/lib/addresses.ts`), so there is nothing invalid to type or reject; a picker/autocomplete removes the error state entirely rather than catching it after the fact.
  - **Layout:** name fields share a row (half-width each). City sits alone on its own full-width row - it's a prerequisite decision, not a peer of street (the street `Combobox` stays disabled, and its option list stays empty, until a city is picked; selecting a city also resets any already-chosen street, since the list is scoped per city). Street then shares a row with building number, sized roughly 2:1 - "street + number" is read and filled as one address unit (e.g. "הרצל 15"), the same pairing convention most address forms use, so it gets its own line rather than being paired with city. A single combined "city + street + number" row (closer to a Waze-style single search field) was considered and rejected: Waze's single line is backed by free-text geocoding across a national address database, not a restricted 2-city/per-city-street-list picker like this one, so a single line here would both look cramped (little room left for long Hebrew street names, which need more space than a 3-way split leaves) and misleadingly imply a flexibility the underlying data doesn't have. Apartment and entrance code (both optional) share the final row, split evenly.
  - **Building number** uses numeric input mode.
- Advances to Step 7 via `"הבא"` - never terminal itself (see "Submission" below).

### Step 7: Confirm

- The single dedicated review-and-submit screen every path ends on, regardless of population - reached from Step 4 (session + profile already complete), Step 5 (phone just verified, already has a profile), or Step 6 (genuinely new phone).
- Renders the read-only order recap described under "Submission" below - for the new-phone population, also including the name/address just entered on Step 6 - plus a `"שלח הזמנה"` button.
- Its own dedicated screen rather than rendered inline at the bottom of whichever step precedes it, for every population (fixed 2026-08-21, generalizing a decision first made 2026-08-20 for the new-phone case alone): stacking a recap card under a step's own interactive content (Step 6's already-full field list, or Step 4/5's own note/photo/phone-OTP content) doesn't reliably fit within the Bottom Sheet's `max-h-[92dvh]` on every viewport - observed as a visible scrollbar inside the sheet on a laptop when Step 4 (Attachments) combined its own content with the recap. No Bottom Sheet screen may ever actually scroll, on any device (see `BottomSheet.tsx`'s doc comment) - splitting into this extra step, not scrolling, is the fix whenever a screen's content doesn't fit on its own.
- `"הקודם"` returns to whichever step preceded it, with every field exactly as left (e.g. see `NewUserDetailsStep`'s `initialValues` prop for the Step 6 case) - this is a real, fully reversible round trip, not a one-way commit.
- **Why this screen exists at all, rather than each preceding step just submitting directly** (considered and rejected 2026-08-20 for Step 6 specifically): the always-available `"הקודם"` button lets a user *fix* a field they already suspect is wrong, but it doesn't help them *notice* one they don't. This is worst for Step 6, since the address is filled field-by-field (city, then street, then a number typed right after it) and never once shown assembled as a single line the way it'll actually be read by a professional - Step 7 is the only point in the flow where that happens (`formatAddressLine`), which is precisely the format a typo like a swapped building number or wrong entrance code tends to actually surface in. For every population, Step 7 is also simply the one point every path shares in common: exactly one recap, exactly one explicit commit tap, regardless of how many steps a given path included.

### Submission

Step 7 (Confirm) is the one screen every path ends on: its primary button reads `"שלח הזמנה"` (not `"הבא"`), and it renders a read-only order recap (category/service, date/time, price or "price after inspection", whether a note/photos were attached) - so every user sees exactly one such recap and taps exactly one explicit commit button, regardless of how many steps their path included. The recap is styled after `ActiveJobCard` (confirmed 2026-08-20, redesigned against Figma node `8483:6420`) - same card shell and structure, full black text, since this is effectively previewing the Job Card the order becomes. It does include a note/photo-attached indicator - reconsidered 2026-08-20 (an earlier pass here had dropped it, reasoning that the eventual Job Card doesn't show one either): the Job Card's omission is fine specifically because that card is a compact list item that defers detail to a tap-through into the full job, note/photos included - this recap has no such tap-through, it's the only point in the flow with no full view of the order before it's created, so a customer genuinely needs the confirmation here that what they attached actually made it in.

- Session + profile already complete → Attachments (Step 4) advances directly to Confirm (Step 7).
- No session, but the verified phone already has a profile → Authentication (Step 5) advances directly to Confirm (Step 7), immediately after OTP verification succeeds.
- No session, and the phone is new → New User Details (Step 6) advances to Confirm (Step 7), which additionally shows the just-entered name/address (see Step 7 above).

**Fixed 2026-08-21:** the first two paths above previously made Step 4/Step 5 themselves terminal - swapping that step's own button to `"שלח הזמנה"` and rendering the recap inline on top of its own content - rather than routing through a shared Step 7 the way the new-phone path always did. Found the same day as the RLS/status-constraint fixes below, testing a second (returning-user) booking end-to-end: the Attachments+recap combination didn't fit `BottomSheet`'s `max-h-[92dvh]` on a laptop viewport, producing a visible in-sheet scrollbar - not acceptable per this doc's Bottom Sheet rule (see `BottomSheet.tsx`). Rather than special-casing a fix for just that one combination, every path now always takes the same extra step to the shared, guaranteed-to-fit Step 7 instead - see `ConfirmStep`'s doc comment.

Submitting creates the Job (and, for a new profile, the `users`/`addresses` rows) as a single atomic operation - see `frontend-architecture.md` once implemented. Job is sent to all professionals in the relevant category; first to accept gets it (per `project-prd.md` Step 6 / `home-screen-prd.md` Flow 5). Flow ends; user sees Job Created confirmation.

**Job Created subtext now varies by SLA tier (confirmed 2026-09-06)** - the single, deadline-less `"נעדכן אותך כשבעל מקצוע יאשר את ההזמנה"` was replaced with two variants, `jobCreated.subtextNearTerm` ("תוך רבע שעה") and `jobCreated.subtextScheduled` ("תוך שעה"), per `project-prd.md` §5 "Scheduled Job Matching." `BookingFlowSheet.submitBooking` picks between them the moment submission succeeds, by comparing that same call's `recap.scheduledTime` against submission time (< 2 hours → near-term tier, otherwise → scheduled/far tier) - a pure client-side computation from data already in hand, not a new backend call. This is documentation + copy only: no `expires_at` column, no expiry cron/edge function, and no professional-facing job queue exist yet to actually enforce either deadline (see that PRD section's "MVP operational mitigation" note for how the SLA is kept in practice today).

**Fixed 2026-08-21:** every submission was failing (`phase` fell to `submit_failed`) because `public.jobs` had row-level security enabled with no insert/select policy - reproduced live via a direct RPC call and confirmed as Postgres error `42501` ("new row violates row-level security policy for table jobs"). Since `submit_booking` is one Postgres transaction, this also silently rolled back the brand-new profile/address rows it had just inserted for a new phone, which is why a customer's just-typed address never appeared to "stick" between separate booking attempts either - both symptoms were the same root cause. Fix (added to `supabase/sql/booking_flow_auth.sql`, §"jobs" RLS): customer-scoped select/insert policies on `public.jobs`, matching the existing pattern already applied for `users`/`addresses`.

**Also fixed 2026-08-21:** the "no_price_yet" population (category matched, no priced catalog service) had no `selectedServiceId` at all, but `jobs.service_id` is a required FK - submitting from that population failed for a second, independent reason. Fixed with one diagnosis-priced placeholder service per category (`supabase/sql/diagnosis_placeholder_services.sql`) - see that file's header comment for why it's one row per category rather than a single shared row (professional-matching has no other way to know a job's category once it has no real service). `BookingFlowSheet` resolves the right placeholder id as soon as this outcome is known and submits with it, entirely invisibly to the customer - the recap still shows no service label and the short "מחיר לאחר אבחון" price line for this population, unchanged.

**Also fixed 2026-08-21 (found right after the RLS fix above, testing the very next submission):** `public.jobs`'s `status` check constraint was out of sync with the documented lifecycle (`order-model.md` "Order Lifecycle" / `JobStatus` in `src/lib/types.ts`) - it only allowed a smaller, different set of values (`pending`, `on_the_way`, `arrived`, `in_progress`, `completed`, `cancelled`), rejecting `submit_booking`'s `'searching_professional'` with Postgres error `23514`. The code/docs were already correct (`searching_professional` is the right first persisted status - `Draft` itself is never written, per the "no partial Job is created" rule above); the constraint hadn't been updated to match. Fixed in `supabase/sql/fix_jobs_status_constraint.sql`, which replaces it with the full 13-state set.

### Address Book

Added 2026-08-23 (see `supabase/sql/address_book.sql`), after noticing a returning customer's second order silently reused their one saved address with no way to see or change it before submitting. Two related product questions came up while designing this:

- **Should a returning customer be asked "which address?" on every app entry, Wolt-style?** No (confirmed 2026-08-23) - a home-services order (this app) is a low-frequency, deliberate action, not a daily-use food-delivery session; asking up front on every open would be friction for the common case (ordering to the same place as last time) to serve the uncommon one. Instead, Step 7 (Confirm) always shows the address that will be used, with a `"שנה כתובת"` button below it (`OrderRecap`'s `onChangeAddress` - moved from beside the address line to its own row 2026-09-04, against Figma node `8576:6550`) - visible before commit, changeable in one tap, invisible the rest of the time.
- **Should a customer be able to save more than one address** (e.g. their own place plus a parent's)? Yes - tapping `"שנה כתובת"` opens `ChooseAddressStep`, a picker over every address `fetchUserAddresses` returns for the account (oldest/first-added first - a stable order, confirmed 2026-09-03, see "Address list order" below) plus an "הוסף כתובת חדשה" row that reuses the same `AddressFields` Step 6 uses. **Select-then-confirm (reworked 2026-08-25):** tapping an existing row only stages it (not an immediate exit) - the customer presses "הבא" in the footer to actually commit and return to Step 7, matching the "select, then press the bottom CTA" pattern every other step in this sheet uses (this button read "המשך לביצוע ההזמנה" until 2026-09-04, when it was shortened to the plain "הבא" every other step's forward button already uses, after the longer wording was observed wrapping to two lines on a narrow phone). Each row's selected state (redesigned 2026-09-04) is shown with a blue border and no background/shadow instead of a leading checkmark - an unselected row keeps the filled off-white background + shadow it always had. Saving a brand-new address is the one exception and still exits straight to Step 7 in one action, since there's nothing else on that screen left to reconsider once a whole new address has just been typed. Only *which already-saved address this order will use* stays a mere in-memory selection until `"שלח הזמנה"` - the address rows themselves persist immediately on "שמור כתובת"/"עדכן כתובת" regardless of submission, see "Immediate persistence" below.
- **Which saved address is shown by default next time?** Whichever one the customer actually used last (confirmed 2026-08-23) - `is_default` on `public.addresses` is flipped onto whatever address a submission used, and off every other one, by `submit_booking` itself. This was chosen over a separately pinned "home" address because it needs no extra UI (no "set as default" affordance anywhere) and matches the actual use case driving this (an occasional order to a parent's place shouldn't permanently bump the customer's own address as "the" default - it already won't, since the parent's address only becomes default if it was the one just used). A fixed pin (e.g. a `label` column) is a possible additive future change if this heuristic ever proves wrong in practice.
- **Address list order (confirmed 2026-09-03, replacing an earlier `is_default`-sorted list).** `ChooseAddressStep`'s list is ordered by `created_at` ascending - the first address ever added stays on top, the most recently added at the bottom, and this never changes again for the lifetime of the account. The previous `is_default`-first sort jumped the most-recently-*used* address to the top of the list every time a different one was used, which read as the list randomly reshuffling itself between orders - confusing, and needlessly so, since with `MAX_TOTAL_ADDRESSES = 3` there's nothing to scroll past either way; a stable order costs nothing and removes that confusion outright. Which row shows as selected is unaffected and still comes from `is_default` - display order and "what's currently selected" are two independent concerns now, not one sort doing double duty. A pleasant side effect: the primary address (`is_primary`, always the first one ever created) now always leads the list too.
- **More than one saved address always routes through `ChooseAddressStep` before ever reaching Step 7 (confirmed 2026-09-03).** Right after Authentication/Attachments (whichever ends up last before Confirm for that path), a returning profile with more than one saved address - counting every one `fetchUserAddresses` returns, including one only ever saved via "שמור כתובת" and never yet used in a submitted order - lands on the address picker automatically, not on Confirm with `is_default` silently pre-selected. Reasoning: quietly defaulting to "whichever was used last" and relying on the customer to notice and correct it on the Confirm recap risked an order actually going out to the wrong address, for exactly the customers this feature exists to serve (anyone who orders to more than one place at all). Exactly one saved address is still a non-choice and skips straight to Confirm, same as before this existed. `BookingFlowSheet`'s `finishChooseAddress` handles returning to Confirm correctly either way this screen is reached - as this new automatic step, or via "שנה כתובת" below.

**Recipient vs. account holder identity:** a customer's name/phone on `public.users` (used for billing/accountability, shown as the top line of `OrderRecap`) never changes based on which saved address is used - confirmed 2026-08-23, considered and rejected swapping it per-address (e.g. showing the parent's name instead of the account holder's when ordering to the parent's place). Instead, each *non-primary* saved address may separately carry an optional `contact_name`/`contact_phone` (settable when the address is first created, in `ChooseAddressStep`'s "add new" view, and fillable/replaceable afterward via its "edit" view - see "Editing a saved address" below) - who the professional should actually expect to meet/call there, shown as a third line in `OrderRecap` only when set - the same `text-sm text-text-primary` as the name/address lines above it (evened out 2026-09-04; it read visibly muted, `text-xs text-text-secondary`, before that). This keeps "who is accountable for this order" and "who the professional will meet" as two separate, independently optional pieces of information, rather than overloading one name field with both meanings.

**The primary address (`is_primary`, added 2026-09-01) never carries a contact override at all.** `public.addresses.is_primary` is `true` for exactly one row per account - the address created together with the profile in Step 6 (`NewUserDetailsStep` + `submit_booking`'s brand-new-profile branch) - and never changes afterward, unlike `is_default` above (which shifts to "most recently used"). This is deliberately a separate, permanent flag, since deriving "the account holder's own original address" from `is_default` doesn't work (that column moves). Two consequences, both confirmed 2026-09-01 after a customer flagged that re-editing their primary address stopped showing their own name once a second order reused it: (1) `ChooseAddressStep`'s edit view shows the account holder's own first/last name (from `public.users`, locked/non-editable) as this address's first line, exactly the way Step 6 originally captured it - not a generic address line with no name at all; (2) the edit view never shows `contact_name`/`contact_phone` fields for it - this address is definitionally the account holder's own place, so "who else should the professional expect to meet here" is never a question for it. This is also what keeps the other-contact math simple: with `MAX_TOTAL_ADDRESSES = 3` and the primary address never eligible for an other-contact, at most the 2 *additional* addresses can ever carry one - exactly `MAX_OTHER_CONTACT_ADDRESSES`.

**First additional address contact prefill:** added 2026-08-28, labels reverted 2026-09-01. `ChooseAddressStep`'s "add new address" view asks for an optional `contact_name`/`contact_phone` (see above) under labels reading "איש קשר בכתובת (אופציונלי)" / "טלפון איש קשר (אופציונלי)" - always these labels, on every additional address including the first. On the very first time an account ever reaches this view at all (adding its second address ever, `usageCounts.totalAddressesCount === 1`), the two fields additionally default to the account holder's own name/phone (`ownName`/`ownPhone` - always known, since `NewUserDetailsStep` requires both before a profile exists at all), with a hint line underneath (`contactFieldsHintFirstTime`) stating the values are pre-filled and can be changed - the fields stay editable, never locked/disabled, so a first additional address that genuinely is for someone else (e.g. a parent's home) can still say so. (A short-lived plain "שם"/"נייד" label variant existed 2026-08-28 through 2026-09-01 for this one case specifically, then was reverted back to the ordinary "(אופציונלי)" labels - only the prefill behavior itself was kept.) Every subsequent additional address (the account's third, ...) gets the same fields with no prefill. The threshold is cumulative like both caps below - a since-deleted second address still counts as "already been through this once" and doesn't re-trigger the prefill on the next add.

**Other-contact cap:** a flat cap on the number of saved addresses outright doesn't, by itself, prevent one account being used on behalf of several unrelated people, since N addresses each naming a different `contact_phone` *is* that exact pattern. So a separate cap targets that signal specifically: only addresses whose `contact_phone` names someone other than the account holder count against `MAX_OTHER_CONTACT_ADDRESSES` (`src/lib/addresses.ts`, currently **2** - reduced from an initial 3 on 2026-08-24 so that, together with the account holder, at most **3 distinct identities** can ever have addresses on one account) - an address with no contact override, or one matching the account holder's own verified phone, doesn't count against this at all. Confirmed 2026-08-25: this counts distinct *phone numbers*, not names - adding just a `contact_phone` to an address counts against the cap the same as adding a full name+phone pair, and a name added alone (no phone) never counts at all. This is enforced in `submit_booking` itself (server-side, authoritative) and pre-checked in `ChooseAddressStep` so the limit shows as an inline explanation next to the contact fields rather than a raw submission failure. Today's business model (customers pay the professional directly; no customer-side subscription yet) means this doesn't block any actual payment circumvention yet, but the same "distinct other-contact count" is the number a future subscription tier would naturally cap instead - laid down now specifically so that future change is a config lookup, not a redesign.

**Total address cap:** added 2026-08-24, as a separate, additional flat ceiling of `MAX_TOTAL_ADDRESSES` (`src/lib/addresses.ts`, currently **3**, reduced from an initial 5 on 2026-08-28 - confirmed decision, since 3 is still comfortably above what a typical customer needs and removes one more number to reason about) on every saved address row, regardless of whose contact is on it. This stacks with the other-contact cap above rather than replacing it - the other-contact cap alone doesn't limit how many properties the account holder saves under their own name, and this closes that gap with a small ceiling that's well above what any legitimate customer needs. Because this cap counts cumulatively including soft-deleted rows (see below), hitting it has no self-service way out - `totalAddressLimitReached`'s copy (`copy-deck.md`) says so explicitly, pointing the customer to contact support instead.

**Both caps count cumulatively, including deleted addresses (confirmed 2026-08-25):** see "Deleting a saved address" below for why - in short, if deleting an address freed up its slot, a customer could delete-and-recreate indefinitely to work around either cap, so both caps count every address a customer has *ever* created, not just the ones currently visible in their list (`fetchAddressUsageCounts` in `src/lib/queries/addresses.ts`, mirroring `submit_booking`'s own server-side counts).

**Editing a saved address:** added 2026-08-24, after a customer asked how to fix a typo'd building number on an address that was only ever selectable, not editable. Each row in `ChooseAddressStep`'s list has its own edit button - a `Pencil` icon trailing the address text inside the row's own pill (icon-only again as of 2026-09-04, having briefly been a visible "ערוך" text link; see `editLinkLabel` in `docs/copy-deck.md`), separate from the row tap, which stays for staging the row as this order's selection - opening an edit form, prefilled, for that address. Never available for the primary address's contact fields at all - see above.
- **`entranceCode` is the only field that stays editable indefinitely** (confirmed 2026-09-03, replacing an earlier "building/apartment/entrance always editable" rule) - a building's door code really does change from time to time. A typo in a locked house number or apartment is a support-side fix, not a self-service one.
- **`buildingNumber`/`apartment` lock per-value the same way contact name/phone do (added 2026-09-03).** Freely replaceable - including clearing apartment back to blank - until that specific value has gone out in a submitted job (`building_number_locked`/`apartment_locked`, flipped by `submit_booking`). A still-blank apartment stays fillable even after earlier jobs used this address without one. Building number is required, so it locks on first submit.
- **City/street are editable for as long as this address hasn't actually been used in a submitted job yet (refined 2026-09-02, from an earlier "always locked, no exceptions" rule).** The original reasoning still holds *after* first use - a different street or city really is a different physical place, i.e. a move, not a correction, which is what "הוסף כתובת חדשה" is for instead of an edit, and it also avoids a saved address quietly starting to mean a different place while a job already references that same row. But that reasoning doesn't apply yet to an address that's only ever been *saved*, never actually used in an order - a customer who picked the wrong street while building their current, not-yet-submitted order needs to be able to just fix it, the same way `buildingNumber`/etc. above already can be. Once `public.jobs` has a row referencing this address (`update_address`'s `v_has_job` check), city/street freeze permanently, same as before.
- **Contact name and contact phone are independently fillable always, and independently *replaceable - including clearing back to blank* - until that specific value has actually gone out in a submitted job (refined 2026-09-01 for replacing, 2026-09-02 for clearing and for the lock itself, all from an earlier "never replaced once set" rule).** Each of the two fields can always be filled in the first time it's blank - so e.g. an address that only ever had a phone saved still allows adding the missing name later, and vice versa (an earlier all-or-nothing version of this rule blocked exactly that case, reported live by a customer whose added name silently failed to save). Beyond that, a value that's already set can also be *replaced*, any number of times, including deliberately clearing it back to blank, but only for as long as that value hasn't itself gone out in a submitted job yet (`contact_name_locked`/`contact_phone_locked` columns, flipped by `submit_booking` at the moment a job is actually created - see `supabase/sql/address_book.sql`'s "Per-value lock, not per-address" note) - this is what lets a customer freely correct, or remove, a just-added contact while still building their current, not-yet-submitted order, while still making it permanent ("locked from next time") the moment a real order has actually gone out using it. Two real bugs found live here, both fixed 2026-09-02: **clearing** - the function used to treat "no value sent" (which is exactly what a deliberately blanked field looks like over the wire) as "field not touched this call" rather than "make this blank", so a cleared contact name/phone silently kept reappearing after save; **per-address vs. per-value locking** - the original version keyed the lock off whether the *address* had ever been used in *any* job at all (`v_has_job`), which wrongly locked a contact name/phone added to an address that already had unrelated job history, even though that specific value had never itself been submitted anywhere - a customer who'd already placed one order with no extra contact, then tried adding one on a second, not-yet-submitted order, found it instantly uneditable. `ChooseAddressStep` mirrors the fixed, per-value signal exactly for its own disabled-field UI via `Address.contact_name_locked`/`contact_phone_locked` (no longer `fetchAddressIdsWithJobs`, which now backs only the city/street lock above).
- **The other-contact cap only ever applies to a genuinely brand-new contact (fixed 2026-08-28, a real bug found live).** Filling in a still-blank phone only re-checks the other-contact cap above when this address had *neither* a name nor a phone before now - not whenever the phone specifically was the blank half. An earlier version keyed this solely off the phone being blank, so completing an address that already had a name saved (exactly the "same contact, just missing one field" case the independent locks above exist to allow) was wrongly treated as adding a brand-new other-contact and could hit the cap - while the mirror direction (filling in a name on an address that already had a phone) never ran any check at all, since the name half never checked anything. Once either half is already set, this address has already been "spoken for" as this order's other-contact slot; completing the other half, or later replacing (or clearing and re-filling) either half, is never a new addition and never re-checks the cap.

Enforced both in the UI (`AddressFields`' `disableLocationFields`, `buildingNumberDisabled`/`apartmentDisabled`, and independent `contactNameDisabled`/`contactPhoneDisabled`) and, authoritatively, in `update_address` itself (`city`/`street` freeze once `v_has_job` is true; `building_number`/`apartment`/`contact_name`/`contact_phone` follow each field's own `_locked` column, including clearing apartment/contact back to `null` while unlocked; `entrance_code` is always overwritten) - see that function's comments in `supabase/sql/address_book.sql`.

The edit screen's own footer (added 2026-08-25) is "חזור" (discards the in-progress edit) and "עדכן כתובת" (commits it) - both return to `ChooseAddressStep`'s list, never straight back to Step 7, keeping the list the one place a selection is actually confirmed (see "Should a customer be able to save more than one address" above).

**Persistence bug, fixed 2026-08-28 (superseded 2026-09-01):** for the first several days after the above shipped, an edit committed via "עדכן כתובת" only ever survived while the customer stayed on `ChooseAddressStep` - continuing to Step 7 via the list's footer "next" action for that *same* address silently discarded the staged edit before `OrderRecap` or `submit_booking` ever saw it (`BookingFlowSheet.onChooseExisting` cleared its `pendingAddressEdit` state unconditionally on every continue, not only when a *different* address was chosen). This made a just-added contact name/phone, or a corrected building number, look "not saved" both immediately (missing from the Step 7 recap) and permanently (never written to `public.addresses`, so a later order showed the old, unedited value again). Patched at the time by only clearing the staged edit when continuing with a different address; the underlying "stage in memory, only persist at final submission" design that made this class of bug possible at all was removed the next iteration below.

**Immediate persistence (2026-09-01), replacing the stage-until-submit design above entirely.** The deeper problem the 2026-08-28 patch only partially addressed: as long as a new/edited address lived purely in `BookingFlowSheet` state (`pendingNewAddress`/`pendingAddressEdit`) until the final `submit_booking` call, it stayed one abandoned order away from silently vanishing - closing the sheet, or any path that never reaches "שלח הזמנה", lost it completely, with no error and no indication anything was wrong. So "שמור כתובת" and "עדכן כתובת" now call two dedicated RPCs - `add_address`/`update_address` (`supabase/sql/address_book.sql`) - the moment either is pressed, independent of whether that particular order ever gets submitted. `submit_booking`'s only remaining address-related responsibility for a returning profile is looking up and verifying ownership of an already-fully-formed `p_address_id` - it no longer creates or edits anything itself except for the one address created together with a brand-new profile (Step 6, still atomic with `submit_booking` since that path has no "come back and re-edit before submitting" loop the way `ChooseAddressStep` does). A related navigation bug from the same root cause is fixed by the same change: previously, pressing "עדכן כתובת" a second time (e.g. from Step 7, "שנה כתובת" → "עדכן כתובת" again) landed back on a blank "add new address" form instead of the list, because a staged-but-unsaved new address had no real id for the picker to select; now that a saved address is always a real row the moment it exists, the picker's `selection` always points straight at it.

**Three follow-up bugs found live right after immediate persistence shipped, all fixed 2026-09-02 (see "City/street" and "Contact name and contact phone" bullets above for the resulting rules):** (1) `ChooseAddressStep`'s edit view unconditionally passed `disableLocationFields` regardless of job history, so a second/third address's city/street locked immediately on save, even though the whole point of immediate persistence was that nothing about a not-yet-submitted order should be frozen yet; (2) `update_address` treated an explicitly-cleared contact name/phone (sent as `null`, indistinguishable over the wire from "not touched this call") the same as "leave it as is", so deleting a mistakenly-added contact and saving silently kept the old value; and (3), reported immediately after (2) shipped, the contact-field lock itself was keyed off the wrong signal - "has this *address* ever been used in *any* job" (`v_has_job`) rather than "has *this value* ever gone out in a job" - so a contact name/phone added to an address that already had unrelated job history (e.g. a first order placed with no extra contact, then a second, not-yet-submitted order adding one) was wrongly locked the instant it was saved. (1) is gated on `v_has_job`; (3) replaced that same signal for contact fields specifically with the new `contact_name_locked`/`contact_phone_locked` columns, flipped only at actual submission time.

**Deleting a saved address is not a customer-facing action (revised 2026-08-31).** A `Trash2` icon per row plus a whole "archive"/restore view (added 2026-08-25/2026-08-28, letting a customer soft-delete a row and later self-service-restore it) existed briefly but was removed - on reflection, for this phase, giving the customer a delete button they can't meaningfully use to free up a slot (see "Both caps count cumulatively" above - deleting never did that) mostly just added a second feature (restore/archive) to explain and maintain, to undo confusion the delete button itself created. `delete_address`/`restore_address` still exist in `supabase/sql/address_book.sql`, soft-deleting the same way (`deleted_at`, never a hard `delete from` - `public.jobs.address_id` must keep pointing at real data, and a hard delete would let a customer cycle through unlimited addresses/contacts over time while staying under both caps at any single snapshot, exactly the abuse both caps exist to prevent) - but `authenticated` no longer has `execute` on either function, so no customer session, including a direct RPC call bypassing the UI entirely, can invoke them anymore. This is now a **service-side-only** capability: callable via the Supabase service-role key (direct SQL, or a future admin/support tool), confirmed 2026-08-31 as the intended split - deletion stays possible for us, never for the customer. Re-enabling it client-side later needs only two things, both preserved in git history: re-adding `grant execute on function public.delete_address to authenticated;` (and the same for `restore_address`), and restoring the removed `ChooseAddressStep` UI.

### Search / AI Matching (within this flow)

- Input: free-text Hebrew problem description or service name from the Home Screen SearchBar (voice input later uses the same pipeline after speech-to-text).
- Matching is a **closed-set classification** against active services in the database (`id`, `label_he`, `keywords`, category, `pricing_type`) - the model must not invent services or prices, and must not use open-web search for discovery or pricing (see `project-prd.md` Sections 10 and 19).
- Pipeline: optional keyword/label prefilter → AI classification when needed → post-process (confidence threshold ~0.55, prefer category-consistent groups, max 3). Implemented in `src/lib/ai/matchServices.ts` / `POST /api/ai/match-services`.
- Reliability: a real job must never be misrouted to "no professionals available" just because the AI call had a transient hiccup. `classifyWithClaudeSonnet` retries once on a thrown/network error or a 429/5xx response, and is guaranteed to resolve to an empty result rather than throw on any failure (a thrown error there would otherwise propagate uncaught and fail the whole search, skipping the fallback below entirely). If AI classification is fully unavailable (missing API key, or still failing after that retry), `matchCategoryByKeywords` (`matchCategory.ts`) is the safety net - a deliberately broad Hebrew keyword list per category, since missing a real job matters more here than an occasional over-eager match.
- Spelling correction: a separate, deliberately tiny/catalog-free AI call (`correctQuerySpelling` in `matchServices.ts`, distinct model from the classification call - see `ANTHROPIC_CORRECTION_MODEL`) runs on **every** search, independent of and in parallel with the keyword/classification pipeline above - including searches that resolve via the keyword prefilter and never call the classification model. This is what fixes obvious Hebrew typos before the query is echoed back to the user (`SearchMatchStep`'s "כתבת: ...") - a keyword hit only guarantees the matched substring itself was typed correctly, not the rest of the sentence, so correction can't be skipped just because a keyword already resolved the match. Kept as a separate lightweight call rather than folded into the (large, full-catalog) classification prompt specifically to avoid paying that prompt's cost/latency on every search just to fix spelling.
- Output: up to 3 service matches (with catalog price ranges), plus a user-facing **"אין התאמה"** option on the sheet.
- Price shown after a catalog service is selected always comes from the catalog row, never from the model.
- The original user query should be retained on the Order draft (notes / problem description) when the booking flow persists it - specifically the typo-corrected version (`matchServices`'s returned `query`), since that's also what's shown to the user throughout the flow.

#### Match outcomes (confirmed)

| Outcome | When | UX |
|---|---|---|
| Priced services | Matcher returns 1–3 catalog services | Search match step → user picks a service (or "אין התאמה") → Next |
| Category without priced service | Category identified, but no suitable priced catalog row (e.g. "לתלות מדפים") | Message `bookingFlow.noPriceYet.*` — professionals exist in the field, price range not defined yet. This outcome skips `SearchMatchStep` entirely, so its heading names the identified category itself (`{category}` template) - otherwise the category the matcher found would never be shown to the user anywhere in this path |

Same back-home CTA as "Unresolved" (`noMatch.backHome`, reused rather than duplicated) |

## 6. Rules

### Rule 1

This is one flow with one implementation, regardless of entry point. Never build a separate Bottom Sheet per entry point (per `ai-engineering-workflow.md`: never create duplicate Components).

### Rule 2

An entry point may only ever skip steps because the corresponding information is already known - never for any other reason.

### Rule 3

Back navigation within the flow returns to the previous **shown** screen (skipped steps/screens remain skipped; they are not revisited going backward). Triggered by a "הקודם" (Previous) button next to that screen's "הבא", shown starting from the second screen in a path (never on the first screen reached in a given entry point) - always rendered active, no disabled state. Returning to a screen restores the answer previously given there (e.g. the picked service, date), rather than showing it empty.

Authentication (Step 5) is a deliberate exception once it's actually verified, not just "shown": going back past it re-treats it as skipped rather than revisiting it, exactly as if a session had already existed when the flow first reached it (confirmed 2026-08-20 - see `BookingFlowSheet`'s `handlePrevious` in `component-library.md`). It's the one screen whose "answer" (a verified session) genuinely can't be restored on the way back the way a picked service or date can - `AuthenticationStep` unmounts once the flow moves on, so its local phone/code state is gone, and re-rendering it fresh would show a blank, unverified-looking form for a user who's already authenticated. Re-verifying a phone that's already verified isn't a real question to revisit; it's just stale UI.

### Rule 4

Closing/dismissing the Bottom Sheet before Submission discards the in-progress Order Draft (no partial Job is created). Aligns with `home-screen-prd.md` Rule 3 ("No state persistence if user exits mid-flow"). A "Discard changes?" confirm dialog may be added in a future version; MVP behavior is discard without persistence.

### Rule 5 — Step Screen Reveal Rule

Each Master Step Sequence step may render as one or more distinct **screens** inside the Bottom Sheet - e.g. Step 3 (Scheduling) is two screens (date, then hour), even though it is one step. A screen may show:

- any number of **informational blocks** (heading/subheading text, no pills) - always shown together as soon as the screen loads, and
- **exactly one question** (heading ± subheading + selectable pills).

Selecting a pill within that question may only reveal/update information already scoped to that same question (e.g. the price line after picking a service) - it must **never** reveal a new question. Advancing to the next screen (its own info blocks + next question) happens **only** when the user presses that screen's "הבא" (Next). This is why a step with more than one question (like Scheduling) must be split into that many screens, each with its own Next - never combined onto a single screen.

**Exception - Authentication's phone/OTP fields:** Step 5's phone input and its inline-revealed OTP code field are not two independent questions the way Scheduling's date and hour are - they're two sequential inputs of one action ("verify your phone"), where the second literally cannot exist until the first has been submitted (there's no OTP to enter before a code has been sent). Revealing the OTP field in place, on the same screen, is treated the same way the price line or a selected-pill's dependent detail is - information scoped to the same question - rather than a second, independent question requiring its own screen.

## 7. Edge Cases

- AI returns no match at all (no category identified) → no-match message + back-home CTA (confirmed).
- User picks "אין התאמה" (a category/services were shown, none fit) → distinct no-service-match message ("try rephrasing"), same back-home CTA (confirmed) - see the Match Outcomes table above.
- No selectable dates/slots within the 6-day window after excluding Fri/Sat (**Needs Confirmation** - undefined fallback).
